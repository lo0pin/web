1. Das Ziel: Ein Raspberry Pi ohne Bildschirm – aber mit eigener Webseite

Anfängerleitfaden · Linux, Python, WLAN, HTML, CSS, JavaScript, BME280, Meshtastic und systemd

Du möchtest einen kleinen Raspberry Pi in ein Mess- oder Steuergerät einbauen, dessen Display dein Smartphone ist. Das funktioniert. Der Pi sammelt Daten und stellt sie über einen Webserver bereit. Dein Handy zeigt eine normale Webseite an; Schaltflächen auf dieser Webseite können Befehle zurück an den Pi senden.

Das gilt beispielsweise für SailSense (Messwerte anzeigen und Gerätefunktionen bedienen) und für ein stationäres RaspbiMesh-/Meshtastic-Setup (Wetterwerte und Funknachrichten ansehen, neue Nachrichten archivieren). Du brauchst dafür grundsätzlich keine Internetverbindung und keinen Cloud-Dienst.

Am Ende kannst du …

  • den Pi erstmals ohne Monitor einrichten,
  • vom PC aus per SSH auf ihn zugreifen,
  • eine Webseite im lokalen Netzwerk aufrufen,
  • Messwerte als JSON an den Browser liefern,
  • Buttons vom Handy an den Pi schicken,
  • optional mit eigenem WLAN-Hotspot arbeiten,
  • Meshtastic-Nachrichten lokal speichern und anzeigen,
  • alles beim Einschalten automatisch starten lassen.

Das wird bewusst NICHT vorausgesetzt

  • Linux-Vorkenntnisse
  • Backend-Programmierung
  • Datenbank-Erfahrung
  • Cloud-Hosting
  • React, Node.js, Flask oder andere Web-Frameworks
  • ein angeschlossener Bildschirm oder eine Tastatur am Raspberry Pi

Der vollständige Praxiscode ist zusätzlich als eigenständiges Beispielprojekt erhältlich. Du kannst die Kapitel Schritt für Schritt durcharbeiten oder die Dateien als fertiges Grundgerüst verwenden. In dieser Anleitung sind die wichtigsten Dateien vollständig einsehbar.

2. Was passiert technisch? Das Prinzip in fünf Bausteinen

BME280 / GPS / SailSense-Logik / Meshtastic-Node
                |       (GPIO, I²C, USB, UART)
                v
         RASPBERRY PI (Linux)
           Python-Programm
                |
          lokale HTTP-API
         GET /api/status
         POST /api/action
                |
       WLAN / Heimrouter / Hotspot
                |
                v
             SMARTPHONE
       Browser: HTML + CSS + JS
        Anzeige und Bedienung

Die Arbeit ist klar getrennt: Python auf dem Pi spricht mit Sensoren, Dateien und Hardware. HTML gibt der Bedienoberfläche ihre Struktur. CSS sorgt für eine brauchbare Darstellung am Handy. JavaScript ruft aktuelle Daten ab und sendet Befehle. Eine API ist die vereinbarte Schnittstelle zwischen Browser und Python.

Begriff Einfach erklärt Im Beispiel
Server Ein Rechner/Programm, das auf Anfragen antwortet. Python auf dem Raspberry Pi
Client Ein Programm, das Daten anfragt oder Befehle sendet. Browser auf dem Smartphone
HTTP Die Sprache der Browser-Anfragen und -Antworten. GET und POST
IP-Adresse Die Adresse eines Geräts in einem Netzwerk. z. B. 192.168.1.42
Port Eine nummerierte „Tür“ zu einem bestimmten Dienst. 8000
JSON Ein kompaktes, maschinenlesbares Datenformat. {"temperature_c": 21.4}
Polling Der Browser fragt in regelmäßigen Abständen neu nach. hier alle zwei Sekunden
systemd Linux-Verwaltung für Programme im Hintergrund. Start nach jedem Boot

WLAN ist nicht das Internet

Diese Unterscheidung ist zentral: WLAN ist zunächst nur eine lokale Funkverbindung. Ein Pi kann mit deinem Handy über WLAN kommunizieren, obwohl weit und breit kein Internet existiert. Die Webseite liegt nämlich auf dem Pi, nicht bei einem externen Anbieter. Ein WLAN-Hotspot des Pi ist somit auf einem Segelboot ebenso denkbar wie in der Werkstatt.

3. Zwei WLAN-Betriebsarten: Heimnetz oder eigener Hotspot

Variante A: vorhandenes WLAN Variante B: Raspberry Pi als Hotspot
Pi und Handy verbinden sich mit demselben Router. Der Pi erzeugt selbst das WLAN; das Handy verbindet sich direkt.
Ideal für Entwicklung, Werkstatt, Wohnung. Ideal für SailSense, unterwegs, Boot oder autarke Station.
Meist Zugang über http://pi-name.local:8000 oder Router-IP. Zugang über die Hotspot-IP des Pi, die du mit ip/nmcli ermittelst.
Internet kann vorhanden sein, ist aber für die lokale Webseite unnötig. Internet ist nicht erforderlich; Android/iOS können „Kein Internet“ anzeigen.

Empfohlene Reihenfolge: Entwickle zuerst im vorhandenen Heim-WLAN. Sobald alles funktioniert, richtest du den Pi als Hotspot ein. Ein einziges WLAN-Interface kann in der üblichen Konfiguration nicht zugleich völlig unabhängig als Hotspot und als Heim-WLAN-Client betrieben werden. Für parallele Verbindungen sind LAN oder ein zweiter WLAN-Adapter die einfache Lösung.

✓ Lernkontrolle: Du kannst erklären, warum ein Browser den Pi erreichen kann, auch wenn der Pi keinen Internetzugang besitzt.

4. Welche Hardware benötigst du?

Teil Benötigt? Worauf achten?

microSD-Karte Ja Ausreichend Platz, vorzugsweise Qualitätskarte; für dauerhaftes Logging auf Haltbarkeit achten.
Passendes Netzteil Ja Stabile Spannung und Stromversorgung nach Pi-Modell; Boot-Probleme kommen oft vom Netzteil.
Windows-, macOS- oder Linux-PC Für Einrichtung Für Imager, SSH und ggf. Dateiübertragung.
Smartphone Für Bedienung Beliebiger moderner Browser genügt.
BME280 Optional Für echte Temperatur-, Feuchte- und Luftdruckwerte.
Meshtastic-Node / Heltec Optional Über USB mit dem Pi verbindbar; die LoRa-Funkstrecke bleibt separat.

Wichtig: Ein Raspberry Pi Pico / Pico W ist nicht dasselbe wie ein Raspberry Pi Zero 2 W. Ein Pico W ist ein Mikrocontroller ohne normales Raspberry Pi OS oder systemd. Auch damit lassen sich Webseiten bauen, aber mit einer völlig anderen Softwarebasis (z. B. MicroPython). Diese Anleitung ist für Raspberry-Pi-Modelle gedacht, auf denen Linux läuft.

Für den ersten Test benötigst du noch keine zusätzliche Sensorik. Eine Systeminformation wie die CPU-Temperatur genügt, um die Verbindung nachzuweisen. Die CPU-Temperatur ist aber ausdrücklich keine Außen- oder Umgebungstemperatur.

5. Raspberry Pi OS installieren – von Null an

  1. Raspberry Pi Imager von raspberrypi.com/software auf deinem PC installieren und öffnen.
  2. Unter „Raspberry Pi Device“ dein konkretes Pi-Modell auswählen.
  3. Als Betriebssystem Raspberry Pi OS Lite wählen: für einen reinen Webserver ist kein grafischer Desktop nötig. Achte darauf, eine zum Pi passende Architektur zu wählen.
  4. microSD-Karte als Speichermedium auswählen. Achtung: Sie wird formatiert.
  5. In der Imager-Konfiguration einen eigenen Benutzernamen, ein starkes Passwort und einen einfachen Hostnamen wie sailsense-pi anlegen.
  6. WLAN-SSID und Passwort deines Heimnetzes hinterlegen; WLAN-Land korrekt auf AT einstellen.
  7. Bei „Remote Access“ SSH aktivieren (für den Einstieg Passwortanmeldung; später besser SSH-Schlüssel).
  8. Image auf die Karte schreiben lassen, Karte in den Pi stecken und den Pi mit geeignetem Netzteil starten. Der erste Start benötigt etwas Zeit.

Du hast nun einen „headless“ Raspberry Pi: kein Monitor, keine Tastatur, keine Maus. Nur Linux im Hintergrund – genau das wollen wir später im abgeschlossenen SailSense-Gehäuse.

Die Imager-Oberfläche und die genauen Registerbezeichnungen können je nach Version variieren. Entscheidend sind: Benutzerkonto, Netzwerk, Hostname, Land und SSH vor dem ersten Start.

6. Die erste Verbindung: SSH vom PC auf den Raspberry Pi

Öffne unter Windows PowerShell oder Windows Terminal. macOS und Linux haben ebenfalls ein Terminal. Mit ssh bekommst du eine Textkonsole auf dem Pi; die eingegebenen Befehle werden auf dem Raspberry Pi ausgeführt.

ssh DEIN_BENUTZER@sailsense-pi.local

Ersetze DEIN_BENUTZER durch den Namen aus Imager, beispielsweise julian. Bei der ersten Verbindung bestätigst du den bekannten SSH-Fingerabdruck nachdem du dich vergewissert hast, dass du den richtigen Pi erreichst, und gibst das Passwort ein. Während der Passworteingabe erscheinen gewöhnlich keine Sternchen: Das ist normal.

Falls .local nicht funktioniert, suche die IP im Router unter „verbundene Geräte“ und nutze beispielsweise:

ssh DEIN_BENUTZER@192.168.1.42

Die IP ist hier ein Beispiel – deine Adresse kann anders aussehen. Mit exit schließt du die SSH-Sitzung.

whoami
hostname
hostname -I
pwd

Diese vier Befehle verraten dir Benutzername, Rechnername, IP-Adressen und aktuelles Verzeichnis. Notiere deine tatsächlichen Werte.

✓ Lernkontrolle: Du kannst vom PC aus eine SSH-Sitzung starten und hostname -I auf dem Pi ausführen.

8. Raspberry Pi aktualisieren und Python vorbereiten

In der SSH-Konsole auf dem Pi:

sudo apt update
sudo apt full-upgrade -y
sudo apt install -y python3 python3-venv python3-pip curl unzip

apt update holt Paketlisten, full-upgrade installiert verfügbare Systemaktualisierungen und apt install sorgt für Python sowie das Werkzeug für virtuelle Python-Umgebungen. Falls ein Neustart empfohlen wird:

sudo reboot

Danach SSH neu verbinden. Du musst diese Installationsschritte nicht bei jedem Start wiederholen.

9. Der erste Webserver in fünf Minuten – noch ganz ohne Sensoren

Wir starten bewusst winzig. Erst wenn du die erste HTML-Seite am Handy siehst, kommt zusätzliche Logik dazu. Sonst suchst du bei Fehlern gleichzeitig in WLAN, Linux, Python, Sensorverdrahtung und HTML – eine unnötige Disziplin im Fehlersport.

  1. Ordner erstellen:
mkdir -p ~/web-test
cd ~/web-test

2. Datei erstellen:

nano index.html

3. Diesen HTML-Inhalt einfügen:

<!doctype html>
<html lang="de">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Mein erster Pi-Webserver</title>
</head>
<body>
  <h1>Hallo vom Raspberry Pi!</h1>
  <p>Diese Seite liegt auf meinem Raspberry Pi.</p>

4. Speichern: in nano mit Ctrl+O, Enter, Ctrl+X. 5. Webserver starten:

6. Smartphone mit demselben WLAN verbinden und im Browser die tatsächliche IP des Pi zusammen mit dem Port öffnen, etwa http://192.168.1.42:8000. Schreibe ausdrücklich http://, nicht https://.

Die IP kannst du in einer zweiten SSH-Verbindung mit hostname -I abrufen. Der Webserver blockiert die erste Konsole, solange er läuft. Das ist vorerst normal.

Mit Ctrl+C beendest du den Testserver. Der Befehl python3 -m http.server kann nur vorhandene Dateien anzeigen; eigene Sensor-APIs und Steuerbefehle fehlen ihm noch.

✓ Lernkontrolle: Auf deinem Handy erscheint „Hallo vom Raspberry Pi!“. Damit sind Netzwerk, IP-Adresse, Port und HTML bereits erfolgreich getestet.

10. Statisch und dynamisch: Wie kommen echte Daten auf die Seite?

Die erste Webseite war statisch. Ihr Text änderte sich nicht, obwohl der Pi im Hintergrund andere Messwerte haben könnte. Für Live-Daten kommt eine HTTP-API hinzu, die in regelmäßigen Abständen einen aktuellen Zustand als JSON zurückliefert.

GET http://192.168.1.42:8000/api/status

Antwort (nur zur Erklärung):
{
  "weather": {
    "temperature_c": 21.4,
    "humidity_percent": 48.2,
    "pressure_hpa": 991.8
  },
  "demo_mode": "standby"
}

Das obige JSON ist ausdrücklich ein Formatbeispiel, keine reale Messung. Der Pi erstellt so eine Antwort, JavaScript wertet sie aus und setzt einzelne Zahlen in HTML-Elemente. Bei fehlendem Sensor werden in unserem echten Beispielprojekt null-Werte zurückgegeben – die Anzeige zeigt „—“ statt Fantasiewetter.

Lesen und Steuern unterscheiden

  • GET fragt einen Zustand ab, ohne ihn verändern zu sollen: Temperatur, Luftdruck, Meldungen, Betriebszustand.
  • POST übermittelt einen Befehl oder neue Daten: „Messung starten“, „Messung stoppen“ oder später „Einstellung speichern“.
  • JSON ist das Transportformat; es sieht nach JavaScript aus, ist aber ein eigenes standardisiertes Datenformat.

12. Projekt starten: Python-Umgebung und sichere PIN

Anders als viele Raspberry-Pi-Tutorials installieren wir keine Python-Pakete ungefragt systemweit. Eine virtuelle Umgebung (.venv) isoliert spätere Bibliotheken. Für den Grundserver benötigst du noch gar keine externe Python-Bibliothek. 

cd ~/pi-web
python3 -m venv .venv
cp .env.example .env
nano .env

In der Datei .env ersetzt du BITTE_DURCH_EIGENEN_PIN_ERSETZEN durch eine lange, selbst gewählte Zeichenfolge. Schreib diese nicht in ein öffentliches GitHub-Repository. Die Datei enthält beispielsweise:

WEB_CONTROL_PIN=HIER_DEIN_EIGENES_LANGES_GEHEIMNIS

Speichern, Leserechte begrenzen und die Variable für den manuellen Test in die aktuelle Konsole laden: 

chmod 600 .env
set -a
. ./.env
set +a
.venv/bin/python server.py

Was passiert nun? Der Webserver startet auf Port 8000. Er stellt die Dateien aus web/ bereit. /api/status liefert Systemwerte. Ohne BME280 sind die Wetterfelder leer; ohne Meshtastic-Bridge ist das Nachrichtenarchiv leer. Die Buttons funktionieren als Demonstration, schalten aber noch keine echte SailSense-Messung um.

Smartphone: http://DEINE-PI-IP:8000 öffnen. Steuer-PIN eingeben, „Demo starten“ drücken, beobachten, wie der angezeigte Zustand wechselt.

Du kannst den Status auch direkt auf dem Pi mit einem zweiten Terminal abfragen:

curl http://localhost:8000/api/status

✓ Lernkontrolle: Das Dashboard lädt am Handy. Die CPU-Temperatur kann angezeigt werden; fehlende Sensorwerte bleiben leer. Nach der PIN-Eingabe verändert der Button den Demo-Zustand.

13. Die Webseite verstehen: HTML, CSS und JavaScript

Im Ordner web/ liegen drei Dateien. Sie entsprechen genau der Architektur deiner GitHub-Pages-Seite: statisches HTML, CSS und Vanilla JavaScript, keine Frameworks. Der Unterschied ist nur die Datenquelle: Statt posts.json vom GitHub-Server abzurufen, fragt diese Seite die lokale API auf dem Pi ab.

HTML: Hier stehen die Platzhalter

<section class="card">
  <h2>Wetter</h2>
  <p>Temperatur: <strong id="temp">—</strong></p>
</section>

Das Element mit id="temp" ist die Adresse innerhalb des Dokuments, an der JavaScript später einen Temperaturwert einsetzt. Du kannst in HTML beliebige weitere Felder für GPS, Luftdruck, Batteriespannung oder Segelparameter ergänzen.

CSS: Deine vorhandenen Bausteine wiederverwenden

Das Dashboard verwendet dieselben Gestaltungsprinzipien wie deine Webseite: :root-Farben, .site-header, .card, .hint und eine responsive Rasterdarstellung. Im Beispielprojekt liegt eine kleine, eigenständige style.css; auf deiner GitHub-Pages-Anleitungsseite nutzt dieses Dokument dagegen direkt dein main.css.

JavaScript: Daten holen und darstellen

async function refresh() {
  const response = await fetch('/api/status');
  const data = await response.json();
  const value = data.weather.temperature_c;
  document.getElementById('temp').textContent =
    value === null ? '—' : `${value} °C`;
}

refresh();
setInterval(refresh, 2000);

fetch() startet eine HTTP-Anfrage. await response.json() wandelt das JSON in ein JavaScript-Objekt um. Mit textContent ersetzt du Text sicher, ohne fremden HTML-Code auszuführen. setInterval(..., 2000) wiederholt die Aktualisierung alle 2000 Millisekunden, also alle zwei Sekunden.

Warum nicht ständig die ganze Seite neu laden?

Die Seite selbst bleibt offen. Es werden lediglich kleine JSON-Antworten übertragen und einzelne DOM-Elemente aktualisiert. Das ist ressourcenschonend, fühlt sich unmittelbar an und genügt für Wetterdaten oder einen Statusmonitor vollkommen. Für sehr schnelle Datenströme können später Server-Sent Events oder WebSockets sinnvoll sein.

14. Der Python-Webserver: Die wichtigsten Funktionen

Die eigentliche Server-Datei heißt server.py. Sie verwendet ThreadingHTTPServer und SimpleHTTPRequestHandler aus der Python-Standardbibliothek. Das ist für einen kleinen, vertrauenswürdigen lokalen Prototypen eine überschaubare Lösung. Ein professioneller, öffentlich erreichbarer Webserver wäre eine andere Liga.

HOST = '0.0.0.0'
PORT = 8000


# GET /api/status   -> aktuelle Werte lesen
# POST /api/action  -> PIN prüfen, Demo-Aktion ausführen
# alle anderen Pfade -> Dateien aus web/ ausliefern

0.0.0.0 ist keine Browser-Adresse. Es bedeutet lediglich, dass der Python-Server auf allen Netzwerkinterfaces des Pi Anfragen annimmt. Du öffnest auf dem Handy weiterhin die konkrete IP oder den Hostnamen des Pi.

In do_GET() werden Zeit, CPU-Temperatur, BME280-Werte, Demo-Zustand und bis zu 20 gespeicherte Mesh-Nachrichten zu JSON. In do_POST() akzeptiert der Server ausschließlich start oder stop und prüft vorher die Steuer-PIN. Unbekannte Befehle werden abgewiesen. Die reale SailSense-Hardware wird noch nicht angesprochen.

Der Demonstrationszustand wird nur im RAM gehalten; nach einem Neustart springt er wieder auf standby. Eine echte Geräteanwendung braucht bei Bedarf dauerhafte Zustandsverwaltung und eine sichere Start-/Stopplogik.

Vollständige Datei anzeigen: server.py

ROOT = Path(__file__).resolve().parent

except (ImportError, RuntimeError, OSError, ValueError) as exc:

def cpu_temperature():

    try:
        raw = Path('/sys/class/thermal/thermal_zone0/temp').read_text().strip()
        return round(int(raw) / 1000, 1)
    except (OSError, ValueError):
        return None


def read_weather():
    if bme is None:
        return {'temperature_c': None, 'humidity_percent': None, 'pressure_hpa': None}
    try:
        with bme_lock:
            return {
                'temperature_c': round(bme.temperature, 1),
                'humidity_percent': round(bme.relative_humidity, 1),
                'pressure_hpa': round(bme.pressure, 1),
            }
    except (OSError, RuntimeError, ValueError) as exc:
        print(f'BME280-Lesefehler: {exc}')
        return {'temperature_c': None, 'humidity_percent': None, 'pressure_hpa': None}


def uptime_seconds():
    try:
        return int(float(Path('/proc/uptime').read_text().split()[0]))
    except (OSError, ValueError, IndexError):
        return None


class Handler(SimpleHTTPRequestHandler):
    def __init__(self, *args, **kwargs):
        super().__init__(*args, directory=str(PUBLIC), **kwargs)

    def send_json(self, status_code, obj):
        raw = json.dumps(obj, ensure_ascii=False, allow_nan=False).encode('utf-8')
        self.send_response(status_code)
        self.send_header('Content-Type', 'application/json; charset=utf-8')
        self.send_header('Content-Length', str(len(raw)))
        self.send_header('Cache-Control', 'no-store')
        self.send_header('X-Content-Type-Options', 'nosniff')
        self.end_headers()
        self.wfile.write(raw)

    def do_GET(self):
        if urlsplit(self.path).path == '/api/status':
            with state_lock:
                mode = state['mode']
            self.send_json(200, {
                'timestamp_utc': datetime.now(timezone.utc).isoformat(),
                'pi_cpu_temperature_c': cpu_temperature(),
                'pi_uptime_seconds': uptime_seconds(),
                'weather': read_weather(),
                'demo_mode': mode,
                'mesh_messages': recent_messages(20),
                'control_available': bool(CONTROL_PIN),
            })
            return
        if urlsplit(self.path).path.startswith('/api/'):
            self.send_json(404, {'error': 'Unbekannter API-Pfad'})
            return
        return super().do_GET()

    def do_POST(self):
        if urlsplit(self.path).path != '/api/action':
            self.send_json(404, {'error': 'Unbekannter API-Pfad'})
            return
        if not CONTROL_PIN:
            self.send_json(503, {'error': 'Steuerung gesperrt: WEB_CONTROL_PIN fehlt'})
            return
        if self.headers.get('Content-Type', '').split(';')[0].strip().lower() != 'application/json':
            self.send_json(415, {'error': 'Bitte JSON senden'})
            return
        try:
            length = int(self.headers.get('Content-Length', '0'))
            if not 0 < length <= 2048:
                self.send_json(413, {'error': 'Anfrage zu gross oder leer'})
                return
            command = json.loads(self.rfile.read(length).decode('utf-8'))
        except (ValueError, UnicodeError, json.JSONDecodeError):
            self.send_json(400, {'error': 'Ungueltige JSON-Daten'})
            return
        if not isinstance(command, dict):
            self.send_json(400, {'error': 'JSON-Objekt erwartet'})
            return
        pin = command.get('pin')
        if not isinstance(pin, str) or not secrets.compare_digest(pin, CONTROL_PIN):
            self.send_json(403, {'error': 'Falsche PIN'})
            return
        action = command.get('action')
        if action not in ('start', 'stop'):
            self.send_json(400, {'error': 'Aktion nicht erlaubt'})
            return
        with state_lock:
            state['mode'] = 'recording' if action == 'start' else 'standby'
            new_mode = state['mode']
        # WICHTIG: Nur DEMO-Zustand. Hier spaeter die SailSense-Funktion aufrufen.
        self.send_json(200, {'ok': True, 'demo_mode': new_mode})


def main():
    prepare()
    if not CONTROL_PIN:
        print('HINWEIS: Demo-Steuerung deaktiviert, da WEB_CONTROL_PIN nicht gesetzt ist.')
    with ThreadingHTTPServer((HOST, PORT), Handler) as httpd:
        print(f'Webserver bereit auf Port {PORT}. Mit Strg+C beenden.')
        httpd.serve_forever()


if __name__ == '__main__':
    main()

16. Echte Wetterdaten: BME280 per I²C anschließen

Jetzt ersetzen wir die leeren Wetterfelder durch reale Daten. Der BME280 misst Temperatur, relative Luftfeuchtigkeit und Luftdruck. Er lässt sich über I²C mit dem Raspberry Pi verbinden – für diese Verbindung sind nur vier Leitungen nötig.

BME280-Pin am Modul Raspberry-Pi-GPIO (BCM) Physische Pin-Nummer
VIN / VCC 3V3 1
GND Masse 6
SDA GPIO 2 / SDA1 3
SCL GPIO 3 / SCL1 5

Elektrische Vorsicht: Diese Tabelle gilt für ein geeignetes 3,3-V-BME280-Breakout. Prüfe stets die Beschriftung und das Datenblatt deines konkreten Moduls, besonders bei Boards mit Regler oder Pegelwandler. Raspberry-Pi-GPIOs sind nicht 5-V-tolerant. Verkabelung nur im ausgeschalteten Zustand ändern.

  1. Pi ausschalten: sudo shutdown -h now, Stromversorgung danach trennen, vier Leitungen korrekt verbinden.
  2. Wieder starten, SSH öffnen und sudo raspi-config ausführen.
  3. Unter Interface Options → I2C die I²C-Schnittstelle aktivieren; bei Bedarf neu starten.
  4. i2c-tools installieren und nach der Sensoradresse suchen.
sudo apt install -y i2c-tools
sudo i2cdetect -y 1

Im Raster sollte typischerweise 76 oder 77 auftauchen. Diese Hexadezimalzahlen entsprechen den I²C-Adressen 0x76 bzw. 0x77. Fehlt beides, zunächst Verdrahtung, Versorgung, Schnittstellenaktivierung und Modul überprüfen.

Python-Treiber installieren (in der virtuellen Umgebung des Projekts):

cd ~/pi-web
.venv/bin/pip install adafruit-blinka adafruit-circuitpython-bme280

Unser server.py versucht beim Start automatisch, den BME280 an 0x76 zu initialisieren. Wenn der I²C-Scan stattdessen 77 meldet, ändere die Adresse im Servercode:

    board.I2C(), address=0x77
)

Danach Server neu starten. Werden Werte erfolgreich gelesen, zeigt das Dashboard Temperatur, Feuchte und Stationsluftdruck an. Stationsdruck ist nicht automatisch der auf Meereshöhe reduzierte Luftdruck aus Wetterberichten.

Wenn du zunächst nur den Sensor testen möchtest

print('Luftdruck:', sensor.pressure)
PY

Ersetze gegebenenfalls auch hier 0x76 durch 0x77. Die Beispielwerte stammen erst nach erfolgreichem Test vom tatsächlichen Sensor.

Für eine Wetterstation gehört der BME280 nicht direkt neben CPU, Akku, Laderegler oder in ein hermetisch geschlossenes, warmes Elektronikgehäuse. Sonst misst du vor allem die Abwärme deiner Elektronik. Temperatur- und Feuchtesensor benötigen eine geschützte, aber belüftete Messposition; für SailSense müssen Salz, Spritzwasser und Feuchtigkeit getrennt betrachtet werden.

17. Meshtastic ist nicht WLAN: Wie die beiden Netze zusammenspielen

Beim Mesh-Teil sind zwei verschiedene Funkwelten beteiligt. Meshtastic überträgt Nachrichten über LoRa auf dem dafür konfigurierten Frequenzband. Dein Handy nutzt für das Dashboard dagegen normales WLAN. Der Raspberry Pi ist die Brücke zwischen beiden.

Ferne Meshtastic-Nodes
       ))))))  LoRa / Meshtastic
                |
       [Heltec / Mesh-Node]
                | USB-Kabel
        [Raspberry Pi]
       Meshtastic Python API
                |
           SQLite-Archiv
                |
      HTTP über WLAN (Pi)
                |
       [Handy im Browser]

Für die ersten Versuche verbindest du einen vorhandenen Heltec-Meshtastic-Node mit einem USB-Datenkabel mit dem Raspberry Pi. Die reguläre Meshtastic-Python-Clientbibliothek kann darüber Textnachrichten empfangen. Du musst dafür nicht den separaten Meshtastic-UART-Serial-Modus aktivieren, solange du über die normale USB-Client-Schnittstelle arbeitest.

Anders als eine bloße Live-Verbindung hat das SQLite-Archiv einen echten Zusatznutzen: Neu eintreffende Nachrichten bleiben lokal gespeichert, selbst wenn du das Handy vom WLAN trennst. Historische Nachrichten vor dem Start des Archivs tauchen dadurch allerdings nicht nachträglich auf.

19. Warum SQLite? Nachrichten und später Messreihen richtig speichern

SQLite ist eine kleine Datenbank, die direkt in einer Datei liegt. Sie benötigt keinen separaten Datenbankserver, ist Teil der Python-Standardbibliothek und eignet sich hervorragend für ein kompaktes Messgerät. Anders als eine bloße Liste im RAM überlebt sie gewöhnliche Neustarts.

messages
┌────┬─────────────────────────┬──────────┬───────────────┐
│ id │ received_at             │ sender   │ message       │
├────┼─────────────────────────┼──────────┼───────────────┤
│  1 │ 2026-...T...+00:00       │ !abcd... │ Hallo Mesh!   │
└────┴─────────────────────────┴──────────┴───────────────┘

Die dargestellte Tabellenzeile ist ein erfundenes Strukturbeispiel. In der echten Datenbank speichert database.py für neue Nachrichten unter anderem Empfangszeit, Absenderkennung, Text und – sofern vorhanden – RSSI/SNR. Die Paket-ID dient der Duplikatvermeidung, soweit sie verfügbar ist.

So liest du die letzten fünf gespeicherten Datensätze aus, ohne ein zusätzliches SQLite-Programm installieren zu müssen:

.venv/bin/python - <<'PY'
from database import recent_messages
for message in recent_messages(5):
    print(message)
PY

Für künftige Wetterverläufe kannst du eine zweite Tabelle hinzufügen, etwa weather_samples(timestamp_utc, temperature_c, humidity_percent, pressure_hpa). Gute Praxis: Messwerte nicht alle 200 Millisekunden auf die SD-Karte schreiben. Sensoren regelmäßig auslesen, sinnvolle Mittelwerte bilden und beispielsweise alle 30–60 Sekunden oder minutenweise dauerhaft speichern. Das begrenzt Speichermenge und Schreibbelastung.

Zeitstempel am besten in UTC speichern und erst im Browser lokal darstellen. Das vermeidet Missverständnisse rund um Sommer- und Winterzeit. Das Beispielarchiv nutzt UTC-Zeitstempel.

Vollständige Datei anzeigen: database.py 
"""Kleine lokale SQLite-Ablage fuer Meshtastic-Nachrichten."""
import sqlite3
from pathlib import Path

DB_PATH = Path(__file__).resolve().parent / 'mesh_messages.sqlite3'


def connect():
    connection = sqlite3.connect(DB_PATH, timeout=10)
    connection.row_factory = sqlite3.Row
    return connection


def prepare():
    with connect() as connection:
        connection.execute('PRAGMA journal_mode=WAL')
        connection.execute('''
            CREATE TABLE IF NOT EXISTS messages (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                received_at TEXT NOT NULL,
                sender TEXT NOT NULL,
                message TEXT NOT NULL,
                rssi REAL,
                snr REAL,
                packet_id TEXT,
                UNIQUE(sender, packet_id)
            )
        ''')


def save_message(received_at, sender, message, rssi=None, snr=None, packet_id=None):
    with connect() as connection:
        connection.execute('''
            INSERT OR IGNORE INTO messages
            (received_at, sender, message, rssi, snr, packet_id)
            VALUES (?, ?, ?, ?, ?, ?)
        ''', (received_at, sender, message, rssi, snr, packet_id))


def recent_messages(limit=20):
    with connect() as connection:
        rows = connection.execute('''
            SELECT received_at, sender, message, rssi, snr
            FROM messages ORDER BY id DESC LIMIT ?
        ''', (min(max(int(limit), 1), 100),)).fetchall()
    return [dict(row) for row in rows]

"""Empfaengt Meshtastic-Textnachrichten von einem USB-Node und archiviert sie."""
import sys
import time
from datetime import datetime, timezone

from database import prepare, save_message

try:
    import meshtastic.serial_interface
    from pubsub import pub
except ImportError:
    raise SystemExit('Zuerst im venv installieren: pip install meshtastic')



def on_receive(packet, interface):
    decoded = packet.get('decoded') or {}
    message = decoded.get('text', '')
    if not isinstance(message, str) or not message:
        return
    sender = str(packet.get('fromId') or packet.get('from') or 'unbekannt')
    packet_id = packet.get('id')
    when = datetime.now(timezone.utc).isoformat()
    save_message(
        when, sender, message, packet.get('rxRssi'), packet.get('rxSnr'),
        str(packet_id) if packet_id is not None else None,
    )
    print(f'[{when}] {sender}: {message}', flush=True)


def main():
    if len(sys.argv) != 2:
        raise SystemExit('Aufruf: python mesh_bridge.py /dev/ttyACM0')
    prepare()
    pub.subscribe(on_receive, 'meshtastic.receive.text')
    # Der serielle Anschluss wird von genau EINEM Prozess verwaltet.
    port = sys.argv[1]
    iface = meshtastic.serial_interface.SerialInterface(devPath=port)
    print(f'Meshtastic verbunden: {port}; warte auf neue Nachrichten ...', flush=True)
    try:
        while True:
            time.sleep(1)
    except KeyboardInterrupt:
        print('Bridge beendet.', flush=True)
    finally:
        iface.close()


if __name__ == '__main__':
    main()

20. RaspbiMesh: Wettertelemetrie und Nachrichten auf einer Oberfläche

Bei deinem RaspbiMesh-Projekt wäre eine gemeinsame Oberfläche ausgesprochen sinnvoll. Allerdings muss man zwischen Messwerten, die direkt am Raspberry Pi entstehen, und Wettertelemetrie, die von einem fernen Mesh-Node per LoRa eintrifft, unterscheiden.

Lokaler BME280 -----------------------┐
                                     |
LoRa-Wettertelemetrie -> USB-Node -> | --> Datenmodell
                                     |       |
LoRa-Textnachrichten -> USB-Node --->|       v
                                     |   SQLite / API
                                     |       |
                                     └-------v
                                         Handy-Dashboard

Die lokalen BME280-Werte kann der mitgelieferte Server direkt anzeigen. Mesh-Wettertelemetrie braucht hingegen einen Decoder für das tatsächlich empfangene Paket: Bei Meshtastic sind das je nach Gerät, Firmware, Portnummer und Sensorsetup andere Felder. Ein selbst entwickeltes RaspbiMesh-Payload-Format wäre wiederum separat zu interpretieren. Die genaue Integration ist daher bewusst noch keine fertige Funktion des Beispielprojekts.

Die richtige Vorgehensweise

  1. Lass die Meshtastic-Bridge zunächst Textnachrichten zuverlässig empfangen.
  2. Untersuche im eigenen Testnetz ein reales empfangenes Telemetriepaket und seine Struktur. Achte darauf, keine privaten Nachrichten oder Schlüssel zu veröffentlichen.
  3. Schreibe einen kleinen Decoder, der die echten Daten in ein einheitliches Format umwandelt, beispielsweise source_node, timestamp_utc, temperature_c und battery_percent.
  4. Speichere die Messwerte in einer eigenen SQLite-Tabelle und ergänze einen API-Endpunkt wie /api/weather-history.
  5. Zeige am Handy sowohl den Messzeitpunkt als auch das Alter des letzten empfangenen Datenpunkts an. „Letzte Meldung vor drei Stunden“ darf nicht wie Live-Wetter aussehen.

Weder die Meshtastic-Funkstrecke noch eine USB-Verbindung garantiert, dass jedes Paket ankommt. Gerade bei einer Wetterstation sind Status „veraltet/offline“, Zeitstempel, Packet-Loss und eine lokale Speicherung nützlicher als eine täuschend glatte „Live“-Anzeige.

21. SailSense: Buttons und OLED durch das Handy ersetzen

Für SailSense ist die Weboberfläche sogar ein potenzieller Gehäuse- und Wartungsgewinn: weniger Ausnehmungen für Taster, keine notwendige Displayöffnung, weniger Dichtungskanten und ein zentraler, am Handy bedienbarer Bildschirm. Die Software muss allerdings so strukturiert sein, dass nicht ein zweiter Webprozess unkontrolliert in die bestehende Sensor- und Logginglogik eingreift.

Bisher am Gerät Mögliches Web-Pendant Technische Umsetzung
OLED: aktuelle Werte Dashboard-Kacheln / digitale Instrumente GET /api/status
OLED: Messverlauf Verlaufsgrafik / Historie GET /api/history + Speicherung
Taste: Start/Stop Zwei große Touch-Schaltflächen POST /api/action
Taste: Menü wechseln Registerkarten / Seitenmenü Lokales HTML/JavaScript
Hardware-Konfiguration Einstellungsformular Validierter POST-Endpunkt
Status-LED Kleine Statusanzeige auf dem Dashboard API-Status plus Anzeige „Letzte Aktualisierung“

Eine zentrale Steuerungslogik statt doppelter Programme

                   +--> physischer Button (optional)
                   |
SailSense-Steuerung +--> Web-POST /api/action
                   |
                   +--> GPS / Sensorik / Logging
                   |
                   +--> Statusdaten -> GET /api/status

Ein robuster Ansatz ist eine zentrale SailSenseController-Klasse oder ein vorhandener Dienst, der die gesamte echte Hardware besitzt. Der Webserver darf nur wohldefinierte Aktionen an diesen Controller weiterreichen und Statuswerte abrufen. Wenn der bestehende SailSense-Dienst schon unter systemd läuft, ist besonders wichtig: nicht gleichzeitig zwei Prozesse mit exklusivem Zugriff auf denselben GPS-/Serial-/GPIO-/I²C-Baustein starten.

Mögliche Integrationswege: A) Webserver direkt im bestehenden Python-Prozess auf einem separaten Thread (mit sauberem Datenaustausch), B) ein getrenntes Webserver-Programm mit lokaler Kommunikation über Socket/Queue/SQLite oder C) der bestehende Prozess schreibt Snapshots, die der Webserver nur liest. Für ein kleines Gerät ist A oft überschaubar; bei mehrjährigem Betrieb kann B eine sauberere Trennung bieten.

Was du beim Entfall von Bildschirm und Tastern nicht übersehen solltest

  • Fallback: Wie stoppst oder startest du wichtige Funktionen, wenn das WLAN ausfällt oder das Handy leer ist? Mindestens eine einfache lokale Notbedienung bzw. definierte Default-Logik ist sinnvoll.
  • Boot-Verhalten: Beginnt die Messung automatisch? Muss sie nach Stromausfall bewusst gestartet werden? Das ist eine Produktentscheidung, keine CSS-Frage.
  • Rückmeldung: Nach einem Buttonklick nur „Erfolg“ melden, wenn die Anwendungslogik die Aktion tatsächlich bestätigt hat.
  • Funk: Ein vollständig leitendes/abgeschirmtes Gehäuse verhindert auch die WLAN-Verbindung. Antenne und wasserdichte HF-Durchführung müssen mitgeplant werden.
  • Energie: WLAN-AP und ständig laufender Pi erhöhen die Leistungsaufnahme. Auf einem Segelboot mit Akku ist das messbar relevant.

22. Ein eigenes WLAN erzeugen: Raspberry Pi als Access Point

Jetzt machen wir das System unabhängig vom Heimrouter. Auf modernen Raspberry Pi OS-Versionen wird das üblicherweise über NetworkManager und das Kommando nmcli konfiguriert. Die folgenden Schritte beruhen auf der offiziellen Raspberry-Pi-Anleitung für Hotspots.

Ganz wichtig vor dem Start: Wenn du aktuell per SSH über wlan0 verbunden bist und dieses Interface zum Hotspot umkonfigurierst, bricht die Verbindung erwartungsgemäß ab. Führe diesen Schritt erst aus, wenn du das Heimnetz-Setup verstanden hast und eine Rückfallmöglichkeit besitzt: Bildschirm/Tastatur, Ethernet/USB-Ethernet oder zweiter WLAN-Adapter. Nicht blind die eigene einzige Fernverbindung kappen.

  1. Prüfe, wie dein WLAN-Adapter heißt und welche Verbindung aktiv ist:
nmcli device

Beim Pi-internen WLAN ist der Name meist wlan0. Andere Geräte können wlan1 heißen. Prüfe außerdem die korrekte WLAN-Ländereinstellung:

sudo raspi-config

Im Menü WLAN-Land auf AT setzen, falls noch nicht geschehen. Jetzt einen Hotspot mit eigener SSID und einem langen Passwort erstellen:

sudo nmcli device wifi hotspot ifname wlan0 ssid SailSense-Local password 'EIN_LANGES_EIGENES_WLAN_PASSWORT'

Das Passwort ist ein Platzhalter und muss ersetzt werden. Der Pi aktiviert das Hotspot-Profil normalerweise sofort. Dein Handy findet anschließend das WLAN SailSense-Local. Verbinde dich mit dem gewählten Passwort.

Die IP des Hotspots feststellen:

ip -4 address show wlan0
nmcli -g IP4.ADDRESS device show wlan0

Oft vergeben NetworkManager-Hotspots eine Adresse im Bereich 10.42.0.x, beispielsweise 10.42.0.1. Verlass dich nicht darauf: Nimm die tatsächlich angezeigte Adresse. Im Handy-Browser rufst du http://DIESE-IP:8000 auf.

Hotspot nach jedem Einschalten automatisch starten

nmcli connection show
sudo nmcli connection modify Hotspot connection.autoconnect yes connection.autoconnect-priority 100

Der Profilname heißt im Standardfall Hotspot; falls er bei dir anders lautet, verwende den angezeigten Namen. Beachte: eine hohe Autoconnect-Priorität macht den Hotspot bewusst zur bevorzugten WLAN-Verbindung. Erwarte dann nicht gleichzeitig eine normale Heim-WLAN-Verbindung über dasselbe Interface.

So kommst du zurück ins Heimnetz

nmcli connection show
# Profilname deines Heimnetzes statt MEIN-HEIMWLAN einsetzen:
sudo nmcli connection up 'MEIN-HEIMWLAN'

Das schaltet die WLAN-Verbindung um und kann eine laufende SSH-Verbindung erneut unterbrechen. Wenn du in Zukunft flexibel zwischen Heimnetz und eigenem Netz wechseln willst, ist ein zweiter WLAN-Adapter oder ein bewusst konzipierter Fallback-Mechanismus besser als spontane Netzwerkschalterei im laufenden Betrieb.

Auf iPhones und Android-Handys kann „WLAN ohne Internet“ erscheinen. Die lokale Webseite funktioniert trotzdem. Bestätige gegebenenfalls, dass das Handy mit dem WLAN verbunden bleiben soll. Achte auf mobile Daten und automatische Netzwechsel, falls der Browser den Pi nicht erreicht.

✓ Lernkontrolle: Du verbindest das Handy direkt mit SailSense-Local und öffnest das Dashboard über die tatsächliche Hotspot-IP, ganz ohne Router.

23. Automatisch beim Einschalten starten: systemd

Ein Webserver, den du nach jedem Boot erst über SSH starten musst, ist noch kein eigenständiges Messgerät. systemd startet Programme im Hintergrund, protokolliert ihren Zustand und kann sie nach einem Absturz neu starten. Du hast ein ähnliches Prinzip bei anderen Raspberry-Projekten bereits im Einsatz.

Schritt 1: Den bisherigen Testprozess beenden

Falls server.py noch in einem Terminal läuft: Ctrl+C drücken. Sonst kann der Dienst später Port 8000 nicht belegen.

Schritt 2: Service-Datei kopieren und anpassen

sudo cp ~/pi-web/pi-web.service.example /etc/systemd/system/pi-web.service
sudo nano /etc/systemd/system/pi-web.service

In dieser Datei musst du jede Stelle DEIN_BENUTZER durch deinen tatsächlichen Linux-Namen ersetzen. Für einen Benutzer julian würde WorkingDirectory=/home/julian/pi-web das richtige Verzeichnis bezeichnen. Die Zeile EnvironmentFile=... liest deine lokale .env mit der Steuer-PIN ein.

sudo systemctl restart pi-web   # nach Codeaenderungen
sudo systemctl stop pi-web      # voruebergehend stoppen
sudo systemctl start pi-web     # wieder starten
sudo systemctl disable --now pi-web  # Autostart deaktivieren

Der Dienst startet auch ohne angemeldeten SSH-Benutzer. Die Umgebung wird aus .env gelesen, daher ist ein vorheriges manuelles source beim Boot nicht nötig.

25. Sicherheit: Für ein Bastelprojekt unkompliziert, aber nicht fahrlässig

Ein Webserver mit Steuerbefehlen ist mehr als eine hübsche Anzeige. Er kann – nach echter SailSense-Anbindung – Hardwarezustände verändern. Deshalb gelten schon beim ersten Aufbau einige simple Regeln.

  • Keine Portfreigabe am Router: Leite Port 8000 nicht ins öffentliche Internet weiter. Das Beispiel ist ausschließlich für ein vertrauenswürdiges lokales Netzwerk gedacht.
  • WLAN schützen: Eigenen Hotspot nur mit sicherem WPA2-/WPA3-Passwort betreiben.
  • Steuer-PIN: Das Beispiel erlaubt keine POST-Aktion ohne gesetztes WEB_CONTROL_PIN. Erstelle eine ausreichend lange, eigene PIN bzw. Passphrase.
  • HTTP ist nicht verschlüsselt: Die PIN wird bei diesem Einsteigeraufbau nicht über TLS geschützt. Für fremde Netze, größere Reichweite und produktive Steuerung brauchst du ein höheres Sicherheitsniveau – etwa HTTPS und richtige Benutzer-/Geräteauthentifizierung.
  • Nur erlaubte Befehle: Der Webserver darf bekannte Aktionen wie Start/Stop annehmen, aber keine beliebigen Shell-Befehle aus einem Browser ausführen.
  • Keine Root-Rechte: Webserver und Meshtastic-Prozess laufen als normaler Linux-Benutzer, nicht als root.
  • Geheimnisse nicht veröffentlichen: .env, WLAN-Passwörter, private Meshtastic-Schlüssel oder Chatarchive gehören nicht ins öffentliche GitHub-Repository.
  • Nachrichten sind fremde Eingaben: Mit textContent im JavaScript wird eingehender Text nicht als HTML ausgeführt; innerHTML mit ungeprüften Funkinhalten wäre unnötig riskant.
  • Offline-Fallback: Ein Gerät soll bei verlorener WLAN-Verbindung einen definierten sicheren Zustand behalten.

Der mitgelieferte Server ist eine Lern- und lokale Prototypenlösung, kein gehärtetes Produkt für öffentliche Netze, medizinische Anwendungen oder sicherheitskritische Steuerungen. WLAN-Zugang und PIN sind nützlich, ersetzen jedoch kein professionelles Sicherheitskonzept.

27. Funk, Gehäuse und Energie: Gerade bei SailSense entscheidend

Ein fensterloses, besser abgedichtetes Gehäuse ist attraktiv. Aber „abgeschirmt“ hat zwei Bedeutungen: gegen Wasser, Staub und mechanische Belastung geschützt ist wünschenswert; gegen Funkwellen abgeschirmt ist bei einem WLAN-gesteuerten Gerät fatal. Ein Metallgehäuse kann den Raspberry Pi praktisch vom Smartphone isolieren.

  • WLAN-Antenne: Eine geeignete Antennenposition oder – je nach Pi-Hardware – externes WLAN mit fachgerechter, wasserdichter Durchführung einplanen. Nicht jeden Pi kann man ohne Modifikation mit externer Antenne ausstatten.
  • LoRa-Antenne: Meshtastic braucht eine eigene, richtig abgestimmte Antenne. WLAN (2,4/5 GHz) und LoRa (in der EU typischerweise 868 MHz) sind getrennte Funkstrecken.
  • Wärme: CPU, Spannungsregler und Akku erwärmen ein geschlossenes Gehäuse. Den BME280 nicht in der heißen Elektronikkammer als „Außentemperaturfühler“ missbrauchen.
  • Kondenswasser und Salznebel: Spritzwasserschutz, Dichtungen, Druckausgleich und geeignete Materialien sind im Bordalltag wichtiger als ein rein optisch dichter 3D-Druck.
  • Versorgung: Pi-Spitzenlasten, USB-Geräte und Hotspot-Betrieb beim Dimensionieren des Akkus berücksichtigen. Ein Pi Zero 2 W ist kein schlafoptimierter ESP32; für Solar-/Batteriestationen ist eine Strombilanz unabdingbar.
  • Startverhalten: Nach Spannungsunterbrechung muss der Pi sauber booten, Sensoren wieder verbinden und seine Weboberfläche auch ohne Handy weiterführen.
  • Speicher: SD-Karten sind kein unendlicher Datenschreiber. Logs begrenzen, Schreibintervalle sinnvoll wählen, Daten exportieren und Backups vorsehen.

Für ein Gerät, das wirklich dauerhaft im Freien oder auf See betrieben werden soll, lohnt es sich, Stromversorgung, Funkkonzept, Gehäuse und Software gemeinsam zu entwerfen statt als voneinander unabhängige Nachrüstungen.

31. Abschlusscheckliste: Wann ist dein System einsatzfähig?

  • Pi startet ohne Monitor und Tastatur.
  • SSH-Zugang funktioniert, und du kennst die aktuelle IP-Adresse.
  • Die lokale Webseite lädt am Handy.
  • /api/status liefert gültiges JSON.
  • Die Anzeige unterscheidet echte Messwerte von fehlenden Daten.
  • Buttons lösen nur erlaubte, geprüfte Befehle aus.
  • Bei echtem BME280 ist Verdrahtung und I²C-Adresse bestätigt.
  • Optional: Meshtastic-USB-Node liefert neue Nachrichten an SQLite.
  • Optional: Der Pi-Hotspot funktioniert ohne Internet.
  • systemd startet die benötigten Dienste selbständig.
  • Die Funktion nach Netz- und Stromausfall ist getestet.
  • Steuerung ist nicht aus dem öffentlichen Internet erreichbar.

Ergebnis: Eine normale Webseite wird zur Bedienoberfläche eines realen Elektronikprojekts. Das Handy ist lediglich der Bildschirm und die Fernbedienung; der Raspberry Pi misst, speichert und steuert selbständig. Genau darin liegt der Vorteil eines headless Geräts.
