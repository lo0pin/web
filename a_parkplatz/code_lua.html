01

Was du hier eigentlich programmierst

Lua ist die Sprache; LOTRO ist die Laufzeitumgebung. Dein Plugin läuft innerhalb des Spielclients. Der Client lädt deinen Code und ruft später bestimmte Funktionen auf, etwa wenn du einen Button anklickst oder eine Chatnachricht eintrifft. Über die Turbine-API erhält dein Code Zugang zu freigegebenen Spieldaten und Oberflächenelementen.

Das ähnelt einem Mikrocontroller-Projekt: Du schreibst Logik in einer Sprache und verwendest die Funktionen, die deine Umgebung bereitstellt. Anders als beim Arduino schreibst du hier aber keine dauernd laufende loop(). LOTRO steuert den Ablauf; dein Plugin reagiert auf Ereignisse.

Ebene Beispiel Aufgabe
Lua local remaining = 12 Werte speichern und verarbeiten
Lua-Standardbibliothek string.format("%.1f", remaining) Zahlen und Texte aufbereiten
LOTRO-API label:SetText("Bereit") Etwas im Spiel anzeigen
Dein eigener Code StartTimer(12) Die Logik deines Plugins organisieren

Die Sprachversion ist wichtig

Schreibe für Lua 5.1, die klassische Grundlage der LOTRO-Pluginumgebung. Beispiele aus Lua 5.3/5.4, Roblox/Luau oder WoW lassen sich nicht unbesehen übernehmen. Insbesondere sind goto, // als Ganzzahldivision, native Bitoperatoren und die eingebaute utf8-Bibliothek keine Lua-5.1-Grundausstattung. continue, += und ++ gehören ebenfalls nicht zu dieser Sprache. Bei Bedarf kannst du die tatsächliche Laufzeit mit _VERSION ausgeben. [1][2]

Was ein Plugin leisten kann

Fenster und Anzeigen bauen, verfügbare Spieler- und Effektdaten lesen, auf Chatereignisse reagieren, eigene Befehle anbieten und Einstellungen speichern: Das sind typische Aufgaben. Die API ist aber kein vollständiger Blick auf den Spielzustand. Ein Gegner-DoT-Tracker braucht andere Überlegungen als eine Anzeige deiner eigenen Buffs.

Ein Button in deinem Plugin kann Lua-Code ausführen. Daraus folgt nicht, dass Lua beliebig Kampffertigkeiten auslösen darf. Quickslots stellen vom Spieler bedienbare Verknüpfungen bereit; eine selbsttätige Rotation ist etwas anderes. Auch beliebiger Dateizugriff, Betriebssystembefehle und Netzwerkzugriff sind keine Grundlage für LOTRO-Plugins.

Die Leitidee dieses Kurses: Erst einen kontrolliert ausgelösten Timer bauen. Danach reale Spielereignisse anschließen. So kannst du einen Fehler in der Zeitrechnung von einem Fehler in der Ereigniserkennung unterscheiden.

So verwendest du die Beispiele

Die Kapitel 2 und 18 enthalten vollständige Dateien. Kapitel 3–10 enthalten kurze Lua-Übungen: Führe sie nach den Imports in deiner kleinen Main.lua aus, jeweils einzeln. Die späteren Ergänzungsbeispiele nennen ihre Voraussetzungen. Nicht alle Codeblöcke hintereinander in dieselbe Datei kleben – das ergäbe eher einen Ork als ein Plugin.

Die Zahlen für Laufzeiten sind Lernwerte, keine Behauptungen über aktuelle Hüter-Gambits. Der Code ist bewusst ohne externe Hilfsbibliotheken geschrieben. Dieses Dokument funktioniert offline; dein beigefügtes classy.css ist eingebettet und um Code-, Tabellen- und Druckstile ergänzt.

02

Die Werkbank: dein erstes Plugin

Du benötigst LOTRO und einen Texteditor, etwa deinen VS Code. Ein separat installierter Lua-Interpreter ist zum Ausführen im Spiel nicht erforderlich. VS Code schreibt die Dateien; LOTRO führt sie aus. Der Startknopf irgendeiner Lua-Erweiterung kennt Turbine normalerweise nicht.

Den richtigen Ordner finden

Suche im tatsächlichen Windows-Dokumenteordner nach The Lord of the Rings Online. Dort liegen üblicherweise auch deine Screenshots und UserPreferences.ini. Der Dokumenteordner kann durch OneDrive umgeleitet sein. Der Installationsordner des Spiels ist hier die falsche Adresse.

Lege diese zwei Dateien an; die Pfade sind relativ zum LOTRO-Dokumenteordner:

Datei Zweck
Plugins/JulianPlugins/LuaWerkstatt.plugin Manifest: Name, Autor, Einstiegspunkt
Plugins/JulianPlugins/LuaWerkstatt/Main.lua Ausführbarer Lua-Code

Achte auf die wirklichen Dateiendungen: Main.lua.txt und LuaWerkstatt.plugin.txt werden dir nur Kummer bereiten. Lass Windows bekannte Dateiendungen anzeigen. Für diese Beispiele kannst du UTF-8 ohne BOM verwenden; die Meldungen im ausführbaren Lernplugin bleiben absichtlich bei ASCII, damit die ersten Schritte nicht an Umlauten scheitern.

Datei 1: LuaWerkstatt.plugin

XML · Manifest
<?xml version="1.0" encoding="UTF-8"?>
<Plugin>
    <Information>
        <Name>LuaWerkstatt</Name>
        <Author>Julian</Author>
        <Version>0.1</Version>
        <Description>Lua lernen direkt in LOTRO</Description>
    </Information>
    <Package>JulianPlugins.LuaWerkstatt.Main</Package>
    <Configuration Apartment="JulianLuaWerkstatt" />
</Plugin>

Das ist XML, nicht Lua. Die Punkte in Package beschreiben den Pfad zum Lua-Einstiegspunkt. Angehängt wird .lua; du schreibst die Endung hier nicht dazu.

Apartment bezeichnet den Skriptzustand, in dem das Plugin läuft. Ein eigener Name hilft, dein Lernplugin getrennt zu entladen. Mehrere Plugins können sich einen Skriptzustand teilen; ein Apartment ist daher nicht einfach ein dekorativer Zweitname. [3]

Datei 2: Main.lua – die erste, vollständige Fassung

Lua 5.1
import "Turbine"
import "Turbine.UI"
import "Turbine.UI.Lotro"

local window = Turbine.UI.Lotro.Window()
window:SetSize(360, 180)
window:SetPosition(200, 200)
window:SetText("Lua-Werkstatt")

local label = Turbine.UI.Label()
label:SetParent(window)
label:SetPosition(20, 50)
label:SetSize(320, 50)
label:SetTextAlignment(Turbine.UI.ContentAlignment.MiddleCenter)
label:SetText("Mellon! Dein Plugin laeuft.")

window:SetVisible(true)
Turbine.Shell.WriteLine("LuaWerkstatt geladen: " .. _VERSION)

Was jede Gruppe von Zeilen bewirkt

  • import lädt LOTRO-Pakete. Es ist eine Erweiterung der Spielumgebung, kein Lua-Schlüsselwort.
  • Window() erzeugt ein Objekt. local window hält eine Referenz darauf.
  • SetSize(360, 180) setzt Breite und Höhe. SetPosition(200, 200) setzt die linke obere Ecke.
  • Das Label ist ein eigenes Objekt. Durch SetParent(window) wird es dem Fenster zugeordnet; seine Position ist dann relativ zum Fenster.
  • SetText verändert die Anzeige. SetVisible(true) blendet das Fenster ein.
  • Turbine.Shell.WriteLine schreibt eine lokale Ausgabe in den Chat. Das ist weder eine Nachricht an Mitspieler noch ein ausgeführter Slash-Befehl.

Laden, ändern, neu laden

Gib im LOTRO-Chat nacheinander ein:

LOTRO · Eingabe
/plugins refresh
/plugins load LuaWerkstatt

Erwartetes Ergebnis: ein Fenster mit Begrüßung und eine Chatmeldung mit der Lua-Version. Wenn du das Fenster über das X schließt, ist das Plugin weiterhin geladen. Für dieses erste Beispiel öffnest du es durch Entladen und erneutes Laden wieder.

Nach Änderungen an Main.lua:

LOTRO · Eingabe
/plugins unload JulianLuaWerkstatt
/plugins load LuaWerkstatt

Beachte den Unterschied: Beim Laden verwendest du den Plugin-Namen, beim Entladen den Apartment-Namen. refresh entdeckt Manifestdateien neu, ersetzt aber keinen bereits laufenden Code. Bei einer Änderung des Manifests entlädst du zuerst, führst refresh aus und lädst erneut. Alternativ hilft der eingebaute Pluginmanager: /plugins manager.

Erste Übung: Ändere Fenstertitel, Größe und Text. Lade neu. Wenn deine Änderung erscheint, funktioniert die gesamte Kette vom Editor bis zum Client.
03

Variablen, Werte und Gültigkeitsbereiche

Eine Variable gibt einem Wert einen Namen. Anders als in C++ legst du keinen festen Variablentyp fest. Der Wert selbst hat einen Typ.

Lua 5.1
local duration = 12          -- number: Sekunden
local skillName = "Test-DoT" -- string: Text
local enabled = true        -- boolean: wahr oder falsch
local target = nil          -- noch kein Ziel gespeichert

Turbine.Shell.WriteLine(type(duration)) -- number
Turbine.Shell.WriteLine(type(target))   -- nil

nil bedeutet: Hier ist kein Wert vorhanden. Das ist etwas anderes als 0, false oder eine leere Zeichenkette. Später kann eine API-Abfrage nil zurückliefern, wenn beispielsweise ein erwartetes Objekt gerade nicht vorhanden ist.

local ist dein Standard

Lua 5.1
local count = 0
count = count + 1

Turbine.Shell.WriteLine(tostring(count)) -- 1

In der zweiten Zeile fehlt local absichtlich: Du änderst die bereits angelegte Variable. Wenn kein passendes local existiert, kann eine Zuweisung stattdessen einen globalen Namen erzeugen. Das macht Tippfehler heimtückisch.

Lua 5.1
local duration = 12
-- FALSCH: Der Tippfehler erzeugt einen anderen Namen.
duraton = 20

Turbine.Shell.WriteLine(tostring(duration)) -- immer noch 12

Eine globale Variable ist kein verlässlicher Kommunikationskanal zwischen sämtlichen Plugins. LOTRO arbeitet mit Skriptzuständen und Paketumgebungen. Für den Einstieg gilt: Zustände lokal halten; gemeinsame Schnittstellen später ausdrücklich definieren.

Blöcke begrenzen die Sichtbarkeit

Lua 5.1
local remaining = 12

if remaining > 0 then
    local message = "Timer aktiv"
    Turbine.Shell.WriteLine(message)
end

-- message ist hier nicht mehr als lokale Variable sichtbar.

Die Variable remaining ist innerhalb des if erreichbar. Umgekehrt ist das dort angelegte message außerhalb nicht erreichbar. Auch Funktionsparameter und Schleifenvariablen sind lokal.

Vorsicht vor versehentlichem Überschatten

Lua 5.1
local remaining = 12

if true then
    local remaining = 5 -- neue, innere Variable!
    Turbine.Shell.WriteLine(tostring(remaining)) -- 5
end

Turbine.Shell.WriteLine(tostring(remaining)) -- 12

Willst du den äußeren Wert ändern, schreibst du im Block remaining = 5. Wiederholtes local bedeutet nicht „besonders lokal“, sondern „lege eine neue Variable an“.

Kommentare und Namen

Einzeilige Kommentare beginnen mit --. Mehrzeilige Kommentare kannst du in --[[ ... ]] einschließen. Lua unterscheidet Groß- und Kleinschreibung: Main, main, SetText und setText sind jeweils verschieden. Verwende in Bezeichnern einfache ASCII-Zeichen, etwa remainingSeconds; deutsche Erläuterungen gehören gern in Kommentare.

04

Rechnen, vergleichen und Entscheidungen treffen

Ein Timer besteht aus zwei Zeitpunkten: jetzt und Ablauf. Die Differenz ist seine Restzeit.

Lua 5.1
local startedAt = 100
local duration = 12
local now = 105

local expiresAt = startedAt + duration
local remaining = math.max(0, expiresAt - now)

Turbine.Shell.WriteLine(tostring(remaining)) -- 7

math.max(0, ...) verhindert negative Anzeigen nach dem Ablauf. Alle Werte sind hier erfundene Sekundenwerte; später liefert Turbine.Engine.GetGameTime() die aktuelle Spielzeit.

Zuweisung x = 5 Kein Vergleich
Gleichheit x == 5 Wie gewohnt
Ungleichheit x ~= 5 Nicht !=
Logisches UND/ODER/NICHT and, or, not Nicht &&, `
Text verketten "Rest: " .. value Nicht +
Potenz 2 ^ 3 Ergibt 8; kein XOR
Rest einer Division 7 % 3 Ergibt 1
Wert erhöhen x = x + 1 Kein x++, kein x += 1

if, elseif, else

Lua 5.1
local remaining = 2.4

if remaining <= 0 then
    Turbine.Shell.WriteLine("Abgelaufen")
elseif remaining <= 3 then
    Turbine.Shell.WriteLine("Bald erneuern")
else
    Turbine.Shell.WriteLine("Noch Zeit")
end

Es wird nur der erste passende Zweig ausgeführt. Das end schließt den gesamten Entscheidungsblock. Klammern um die Bedingung sind optional; then ist erforderlich.

Die berühmte Null-Falle

In Lua sind nur false und nil falsch. 0, "" und eine leere Tabelle gelten in Bedingungen als wahr.

Lua 5.1
local remaining = 0

if remaining then
    Turbine.Shell.WriteLine("Diese Zeile erscheint trotz 0.")
end

if remaining > 0 then
    Turbine.Shell.WriteLine("Diese Zeile erscheint nicht.")
end

Eine Prüfung wie if remaining then sagt lediglich: Der Wert ist weder nil noch false. Sie sagt nicht: Der Timer läuft.

Kurzschlussauswertung schützt vor nil

Lua 5.1
local timer = nil

if timer ~= nil and timer.remaining > 0 then
    Turbine.Shell.WriteLine("Aktiv")
end

Der rechte Teil von and wird nur ausgewertet, wenn der linke wahr ist. Dadurch wird bei nil gar nicht erst auf timer.remaining zugegriffen.

or eignet sich für manche Standardwerte: local title = suppliedTitle or "Timer". Aber false wird dadurch ebenfalls ersetzt. Eine gespeicherte Einstellung „deaktiviert“ darfst du daher nicht mit settings.enabled or true laden. Prüfe dort gezielt auf nil oder auf den erwarteten Typ.

05

Texte, Zahlen und die Eigenheiten des Kampfchats

Ein Plugin übersetzt Daten ständig in sichtbare Texte. Lua verwendet dafür Strings.

Lua 5.1
local name = "Test-DoT"
local remaining = 7.236

local text = name .. ": " .. string.format("%.1f s", remaining)
Turbine.Shell.WriteLine(text) -- Test-DoT: 7.2 s

%.1f formatiert eine Zahl mit einer Nachkommastelle. %s steht für Text; für eine bereits ganzzahlige Zahl kannst du %d verwenden. tostring(...) eignet sich für Debugausgaben, insbesondere bei nil oder Wahrheitswerten.

Benutzereingaben prüfen

Lua 5.1
local input = "15"
local duration = tonumber(input)

if duration == nil or duration <= 0 or duration > 120 then
    Turbine.Shell.WriteLine("Bitte eine Dauer von 1 bis 120 eingeben.")
else
    Turbine.Shell.WriteLine("Dauer: " .. tostring(duration))
end

tonumber("Unsinn") ergibt nil. Rechne erst nach der Prüfung mit dem Wert. Für ein eigenes Eingabeformat ist ein Dezimalpunkt am unkompliziertesten; ein deutsches Komma solltest du ausdrücklich behandeln, wenn du es zulassen möchtest.

Text finden: zunächst ohne Muster

Lua 5.1
local message = "Test-DoT verursacht Schaden."
local skillName = "Test-DoT"

local first, last = string.find(message, skillName, 1, true)
if first ~= nil then
    Turbine.Shell.WriteLine("Name gefunden ab Position " .. first)
end

Die letzten beiden Argumente bedeuten: Suche ab Position 1 und behandle den Suchtext wörtlich. Das true ist wichtig, wenn ein Name Zeichen wie -, ( oder . enthält: Ohne Klartextmodus können sie als Musterzeichen interpretiert werden.

Lua-Patterns sind keine vollständigen regulären Ausdrücke

Lua 5.1
local message = "TEST damage=1234"
local digits = string.match(message, "^TEST damage=(%d+)$")
local damage = tonumber(digits)

if damage ~= nil then
    Turbine.Shell.WriteLine("Testschaden: " .. damage)
end

Das ist ein künstliches Testformat, keine echte LOTRO-Kampfmeldung. ^ und $ begrenzen Anfang und Ende; %d+ bedeutet eine oder mehrere Ziffern; die Klammern liefern den gefundenen Teil zurück. Lua-Patterns besitzen beispielsweise kein Regex-Alternativzeichen | im üblichen Sinn.

Bei echten Kampfmeldungen musst du Sprache, Satzbau, kritische Treffer und Zahlendarstellung berücksichtigen. Ein Ausdruck für 1234 versteht 1.234 nicht automatisch richtig. Erst echte Meldungen sammeln, dann Parser schreiben.

Umlaute sind kein nebensächliches Detail

Lua 5.1 behandelt Strings grundsätzlich als Bytefolgen. #text zählt Bytes, und string.sub kann bei UTF-8 einen mehrbyteigen Buchstaben zerschneiden. Auch string.lower ist keine allgemeine Unicode-Normalisierung. Für deutsche Fertigkeitsnamen sind exakt übernommene Texte in passender Kodierung zuverlässiger als selbstgebastelte „alles kleinschreiben“-Magie. Prüfe zunächst, wie ein Name im tatsächlichen Client ankommt.

06

Tabellen: das wichtigste Werkzeug der Sprache

Mit einer table baust du Listen, Nachschlagewerke und eigene Datenobjekte. Es gibt nicht für jeden dieser Fälle einen separaten eingebauten Container-Typ.

Eine Liste für eine feste Anzeigereihenfolge

Lua 5.1
local order = { "spear", "light", "bleed" }

Turbine.Shell.WriteLine(order[1]) -- spear
Turbine.Shell.WriteLine(tostring(#order)) -- 3

table.insert(order, "test")
table.remove(order, 2) -- entfernt light; folgende Eintraege ruecken nach

Lua-Listen beginnen konventionsgemäß bei 1. Tabellen können auch einen Schlüssel 0 haben; die üblichen Listenfunktionen erwarten aber eine lückenlose Folge ab 1. # ist deshalb keine allgemeine Zählfunktion für beliebige Tabellen.

Ein Nachschlagewerk für Timerdefinitionen

Lua 5.1
local definitions = {
    spear = { label = "Speer-Test", duration = 12 },
    light = { label = "Licht-Test", duration = 18 },
    bleed = { label = "Blutungs-Test", duration = 15 }
}

local selectedId = "spear"
local definition = definitions[selectedId]

Turbine.Shell.WriteLine(definition.label)
Turbine.Shell.WriteLine(tostring(definition.duration))

Die IDs und Laufzeiten sind frei gewählte Lernwerte. Der Vorteil stabiler interner IDs: Du kannst später die Anzeige übersetzen, ohne die gesamte Logik von deutschen Fertigkeitsnamen abhängig zu machen.

definitions.spear und definitions["spear"] sind gleichbedeutend. definitions[selectedId] verwendet den Wert der Variablen als Schlüssel. definitions.selectedId würde dagegen einen Eintrag mit dem wörtlichen Namen selectedId suchen.

Eintrag löschen und Existenz prüfen

Lua 5.1
local activeTimers = {}
activeTimers.spear = { expiresAt = 112 }

if activeTimers.spear ~= nil then
    Turbine.Shell.WriteLine("Timer existiert")
end

activeTimers.spear = nil -- entfernt den Eintrag

Bei einer Liste erzeugt das Setzen eines mittleren Elements auf nil eine Lücke. ipairs endet am ersten fehlenden Index; # ist für eine solche löchrige Liste nicht die erhoffte Anzahl. Verwende bei geordneten Listen table.remove oder baue die Liste bewusst neu auf.

Tabellen werden nicht automatisch kopiert

Lua 5.1
local original = { duration = 12 }
local alias = original
alias.duration = 20

Turbine.Shell.WriteLine(tostring(original.duration)) -- 20

Beide Variablen verweisen auf dieselbe Tabelle. Für eine unabhängige flache Kopie:

Lua 5.1
local defaults = { duration = 12, enabled = true }
local settings = {}

for key, value in pairs(defaults) do
    settings[key] = value
end

settings.duration = 20

Verschachtelte Tabellen würden bei dieser flachen Kopie weiterhin gemeinsam verwendet. Für den Anfang reichen flache Einstellungen oder bewusst neu angelegte Untertabellen.

07

Schleifen, ohne den Client festzunageln

Eine Schleife arbeitet ihre Wiederholungen unmittelbar ab. Sie wartet nicht automatisch auf den nächsten Frame.

Lua 5.1
for i = 1, 3 do
    Turbine.Shell.WriteLine("Zeile " .. i)
end

Die Grenzen sind einschließlich: Diese Schleife gibt 1, 2 und 3 aus.

ipairs für Listen, pairs für Schlüssel

Lua 5.1
local order = { "spear", "light", "bleed" }

for index, id in ipairs(order) do
    Turbine.Shell.WriteLine(index .. ": " .. id)
end

local durations = { spear = 12, light = 18 }
for id, duration in pairs(durations) do
    Turbine.Shell.WriteLine(id .. " dauert " .. duration)
end

ipairs besucht die lückenlose Zahlenfolge. pairs besucht vorhandene Schlüssel; ihre Reihenfolge ist nicht garantiert. Für eine dauerhaft gleich sortierte Oberfläche nimmst du eine explizite Reihenfolgeliste.

Beim Entfernen aus einer Liste rückwärts gehen

Lua 5.1
local timers = {
    { name = "A", remaining = 0 },
    { name = "B", remaining = 4 },
    { name = "C", remaining = 0 }
}

for i = #timers, 1, -1 do
    if timers[i].remaining <= 0 then
        table.remove(timers, i)
    end
end

Beim Vorwärtslaufen verschieben sich nach einer Entfernung die Indizes. So kann ein Element übersprungen werden. Rückwärtslaufen vermeidet dieses Problem.

while bedingung do ... end und repeat ... until bedingung gibt es ebenfalls. repeat führt den Rumpf mindestens einmal aus. break verlässt eine Schleife. Verwende diese Werkzeuge für begrenzte Arbeit, etwa das Bearbeiten einer kleinen Warteschlange.

Keine Warteschleife für Timer. Ein while true do ... end oder eine Schleife, die mehrere Sekunden auf eine Uhrzeit wartet, blockiert die Skriptausführung und kann den Client einfrieren. Ein Countdown reagiert auf Update-Ereignisse und gibt die Kontrolle dazwischen sofort zurück.
08

Funktionen, Rückgaben und Closures

Funktionen bündeln eine Aufgabe. Parameter erhalten beim Aufruf Werte; return liefert Ergebnisse und beendet den Funktionsaufruf.

Lua 5.1
local function Remaining(expiresAt, now)
    return math.max(0, expiresAt - now)
end

local seconds = Remaining(112, 105)
Turbine.Shell.WriteLine(tostring(seconds)) -- 7

Die Funktion kennt keine Fenster und keine Spielobjekte. Trotzdem ist sie vollständig auf unseren Pluginzweck zugeschnitten. Solche kleinen Berechnungen lassen sich leichter überprüfen als ein großer Block aus UI, Parsing und Zeitrechnung.

Mehrere Rückgabewerte

Lua 5.1
local function ParseDuration(text)
    local value = tonumber(text)
    if value == nil or value < 1 or value > 120 then
        return nil, "Erlaubt sind 1 bis 120 Sekunden."
    end
    return value, nil
end

local duration, errorMessage = ParseDuration("18")
if duration == nil then
    Turbine.Shell.WriteLine(errorMessage)
else
    Turbine.Shell.WriteLine("OK: " .. duration)
end

Hier ist der erste Rückgabewert das Ergebnis und der zweite eine mögliche Fehlermeldung. Fehlende Argumente erhalten nil. Lua überprüft nicht von selbst, ob der Aufrufer die richtigen Datentypen liefert.

Eine Funktion ist selbst ein Wert

Lua 5.1
local function SayReady()
    Turbine.Shell.WriteLine("Bereit")
end

local callback = SayReady -- Funktion merken
callback()                -- Funktion jetzt ausfuehren

SayReady und SayReady() sind fundamental verschieden: Das erste bezeichnet die Funktion, das zweite ruft sie auf. Ein Eventhandler braucht üblicherweise die Funktion, nicht deren gerade berechneten Rückgabewert.

Closure: die Funktion behält Zugang zu ihrem Umfeld

Lua 5.1
local function CreateCounter()
    local count = 0

    return function()
        count = count + 1
        return count
    end
end

local nextCount = CreateCounter()
Turbine.Shell.WriteLine(tostring(nextCount())) -- 1
Turbine.Shell.WriteLine(tostring(nextCount())) -- 2

Die zurückgegebene Funktion greift auch nach dem Ende von CreateCounter auf dessen lokale Variable zu. Diese Verbindung heißt Closure. Genau deshalb kann ein Klick-Handler später noch den Timerzustand verändern, den du beim Laden des Plugins angelegt hast.

Der gespeicherte Zustand bleibt erhalten, solange entsprechende Referenzen bestehen. „Die Datei ist fertig durchgelaufen“ bedeutet bei einem Plugin also nicht „alle lokalen Variablen sind verschwunden“.

Punkt, Doppelpunkt und self

Dieses Kapitel erspart dir eine überraschende Menge Fluchen.

Lua 5.1

end

Turbine.Shell.WriteLine(tostring(timer.remaining)) -- 8

timer.SetRemaining(8) wäre dagegen falsch: Die 8 würde an der Stelle des Objekts ankommen. Wenn der Code anschließend auf self.remaining zugreift, passt der Typ nicht mehr.

Daten, Zustand und Darstellung auseinanderhalten

Ein guter Tracker unterscheidet mindestens drei Dinge:

Bereich Beispiel Lebensdauer
Definition „Test A dauert 12 Sekunden“ Bleibt normalerweise gleich
Laufender Zustand „Test A läuft bis Spielzeit 112“ Ändert sich während des Spiels
Darstellung Label, Balken, Farbe Zeigt den Zustand an
Lua 5.1

    test = { label = "Test A", duration = 12 }
}
local active = {}

local function StartTimer(id, now)
    local definition = definitions[id]
    if definition == nil then
        return false
    end

    active[id] = {
        expiresAt = now + definition.duration

Ein Balken ist oft nur ein Rechteck

Für einen simplen Fortschrittsbalken brauchst du keine komplizierte Spezialklasse. Ein Control als Hintergrund und ein zweites als farbige Füllung reichen. Die Füllbreite berechnet sich aus:

Lua 5.1
local remaining = 6
local duration = 12
local maximumWidth = 280
local fraction = math.max(0, math.min(1, remaining / duration))
local width = math.floor(maximumWidth * fraction)
-- width ist 140. Im echten UI: fill:SetWidth(width)

math.min und math.max begrenzen den Anteil auf 0 bis 1; math.floor rundet ab. Voraussetzung ist eine positive Dauer. Die vollständige Oberfläche findest du in Kapitel 18.

Koordinaten und Farben

SetPosition(x, y) meint links/oben; x wächst nach rechts, y nach unten. Bei Kind-Controls sind die Koordinaten relativ zum Elternobjekt. Ein Fenster ist ein Objekt auf oberster Ebene; für innere Container verwendest du Control, nicht ein zusätzliches Kindfenster. [4]

Bei Turbine.UI.Color(r, g, b) liegen die Farbkanäle zwischen 0 und 1. Color(0.2, 0.6, 0.8) ergibt ein Blau. Ein weiterer Konstruktor nimmt Alpha vor den Farbkanälen entgegen. Verwechsle diese Werte nicht mit CSS-RGB-Zahlen von 0 bis 255.

Setze Größen ausdrücklich. Ein vorhandenes Label kann trotzdem unsichtbar wirken, weil es außerhalb seines Containers liegt, keine sinnvolle Größe hat oder Textfarbe und Hintergrund kaum unterscheidbar sind.

Events ordentlich anmelden und wieder entfernen

Dein eigener Button gehört dir. Dort ist button.Click = ... im kleinen Plugin übersichtlich. Bei gemeinsam verwendeten Ereignisquellen wie Turbine.Chat oder der Effektliste solltest du vorhandene Handler dagegen nicht blind ersetzen.

In LOTRO begegnet dir häufig das Muster, in einem Ereignisfeld entweder eine Funktion oder eine Liste von Funktionen abzulegen. Die Namen AddCallback und RemoveCallback sind keine eingebauten Lua-Schlüsselwörter und nicht automatisch vorhanden. Du musst solche Hilfsfunktionen selbst definieren oder bewusst aus einer Bibliothek importieren. [5]

Ein überschaubares Hilfspaar

Setze diese beiden lokalen Funktionen nach die Imports, bevor du sie benutzt:

Lua 5.1
local function AddCallback(object, eventName, handler)
    local current = object[eventName]

    if current == nil then
        object[eventName] = handler
    elseif type(current) == "function" then
        if current ~= handler then
            object[eventName] = { current, handler }
        end
    elseif type(current) == "table" then
        for _, existing in ipairs(current) do
            if existing == handler then
                return -- denselben Handler nicht doppelt eintragen
            end
        end
        table.insert(current, handler)
    else
        error("Unerwarteter Eventtyp: " .. type(current))
    end
end

local function RemoveCallback(object, eventName, handler)
    local current = object[eventName]

    if current == handler then
        object[eventName] = nil
    elseif type(current) == "table" then
        for i = #current, 1, -1 do
            if current[i] == handler then
                table.remove(current, i)
            end
        end

        if #current == 0 then
            object[eventName] = nil
        elseif #current == 1 then
            object[eventName] = current[1]
        end
    end
end

Das Beispiel behandelt die übliche lückenlose Handlerliste. Es ist kein universeller Ereignisverteiler für beliebige Fremdbibliotheken. Insbesondere sollten Handlerlisten nicht mitten in ihrer eigenen Abarbeitung umgebaut werden. Hier melden wir beim Aufbau an und beim Beenden ab.

Du musst dieselbe Funktion wiederfinden

Lua 5.1
-- Voraussetzung: AddCallback und RemoveCallback von oben.
local function OnChat(sender, args)
    -- Hier spaeter die eigentliche Verarbeitung.
end

AddCallback(Turbine.Chat, "Received", OnChat)

-- Beim Aufraeumen:
RemoveCallback(Turbine.Chat, "Received", OnChat)

Eine neu geschriebene function(sender, args) ... end wäre ein anderes Funktionsobjekt, selbst wenn ihr Inhalt identisch ist. Deshalb behältst du die ursprüngliche Referenz.

Der Lebenszyklus gehört zum Plugin

Beim Laden steht die temporäre Referenz plugin zur Verfügung. An diesem konkreten Pluginobjekt kannst du den Unload-Handler registrieren: [4]

Lua 5.1
-- Voraussetzung: Kapitel-2-Fenster und die Helfer/OnChat von oben.
local thisPlugin = plugin

thisPlugin.Unload = function(sender, args)
    RemoveCallback(Turbine.Chat, "Received", OnChat)
    window:SetWantsUpdates(false)
    window:SetVisible(false)
end

Wenn bereits ein Unload-Handler existiert, ergänze dessen Rumpf. Definiere nicht einfach einen zweiten und verliere dabei das erste Aufräumen. Turbine.Plugin.Unload ist nicht der Platz, um deinen individuellen Plugin-Lebenszyklus zu organisieren.

Echte Spielinformationen: Spieler und eigene Effekte

Lua 5.1

Änderungen beobachten

Füge die beiden Helfer aus Kapitel 12 nach den Imports ein. Ergänze dann unter dem obigen Code:

local function OnEffectAdded(sender, args)
    local effect = args.Effect
    if effect == nil and args.Index ~= nil then
        effect = sender:Get(args.Index)
    end

    if effect ~= nil then
        Turbine.Shell.WriteLine("Neu: " .. effect:GetName())
    end

Wenn dein Buff schon aktiv war, bevor du das Plugin lädst, entsteht durch das Laden kein neues EffectAdded-Ereignis. Der Anfangsscan erfasst den vorhandenen Zustand; Events halten ihn anschließend aktuell. Dieses Muster taucht in Plugins ständig auf.

Eigene Buffs sind ein guter nächster Schritt. Für Effekte auf Gegnern darfst du nicht voraussetzen, dass dieselben Informationen gleichermaßen verfügbar und vollständig sind. Lies die aktuelle API-Beschreibung des konkreten Objekts und überprüfe Werte im Client.

Kampfchat lesen, ohne sich selbst etwas vorzumachen

Turbine.Chat.Received meldet Chatereignisse. Über args.ChatType filterst du den Kanal, über args.Message liest du den Text. [7]

Für eine gezielte Untersuchung genügt dieser Handler. Voraussetzung: Imports aus Kapitel 2 und die beiden Callback-Helfer aus Kapitel 12. Dieses Beispiel kommt in eine eigene Diagnosefassung der Main.lua, nicht ungeprüft zusätzlich zu anderen Unload-Handlern.

Lua 5.1
local watchedText = "HIER EXAKTEN FERTIGKEITSNAMEN EINTRAGEN"
local seen = 0

local function OnCombatChat(sender, args)
    if args.ChatType ~= Turbine.ChatType.PlayerCombat then
        return
    end

    if type(args.Message) ~= "string" then
        return
    end

    if string.find(args.Message, watchedText, 1, true) == nil then
        return
    end

    if seen >= 10 then
        return -- Diagnoseausgabe begrenzen
    end

    seen = seen + 1
    Turbine.Shell.WriteLine("[LW Probe] " .. args.Message)
end

AddCallback(Turbine.Chat, "Received", OnCombatChat)

plugin.Unload = function(sender, args)
    RemoveCallback(Turbine.Chat, "Received", OnCombatChat)
end

Das Echo wird als normale lokale Ausgabe geschrieben; der Handler verarbeitet nur PlayerCombat. So vermeidest du, dass deine eigene Debugausgabe erneut als Treffer verarbeitet wird. Die Begrenzung verhindert, dass der Chat unter Diagnosemeldungen begraben wird.

Der entscheidende Denkfehler beim DoT-Tracker

Der folgende Gedanke ist verführerisch: „Wenn der Fertigkeitsname in der Nachricht steht, starte ich ihre Laufzeit neu.“ Das funktioniert nur, wenn dieser Text den relevanten Start tatsächlich eindeutig bezeichnet.

Bei periodischem Schaden kann derselbe Name bei jedem Tick auftauchen. Dann würde ein naiver Tracker seinen Timer fortwährend verlängern. Dazu kommen mehrere Ziele, Widerstehen, kritische Treffer, Verzögerungen und Meldungen anderer Akteure.

Beobachtung Was du daraus zunächst ableiten kannst
Name taucht in einer Nachricht auf Die Nachricht erwähnt den Namen
Eigene passende Schadensmeldung Schaden wurde gemeldet; nicht zwingend ein neuer Einsatz
Verlässlich beobachteter Effektbeginn Der beobachtete Effekt ist erschienen
Manuell ausgelöster Test Der Spieler hat den Test ausgelöst

Ein solider Entwicklungsweg

  1. Fertigkeit einmal auf ein einzelnes Ziel anwenden; sämtliche dazugehörigen Meldungen beobachten.
  2. Direkt danach nichts tun und die periodischen Meldungen sammeln.
  3. Erneut anwenden; untersuchen, ob der neue Einsatz im Text unterscheidbar ist.
  4. Widerstehen, mehrere Ziele und einen Zielwechsel getrennt testen.
  5. Nur die nachgewiesenen Fälle automatisieren; eine Schätzung auch als Schätzung anzeigen.

Ein bloßer „Cooldown gegen doppelte Meldungen“ kann Symptome kaschieren, beweist aber keine korrekte Erkennung. Für den ersten Kurs bauen wir deshalb einen ehrlichen manuellen Testtimer. Dessen Startsignal ist eindeutig, und du lernst daran dieselbe Anzeige- und Zeitlogik.

Zeitmessung und Update: der eigentliche Countdown

Ein Countdown zählt nicht Frames. Er berechnet bei jeder Aktualisierung, wie viel Zeit bis zum Ende bleibt.

Lua 5.1
-- Kurzes Rechenbeispiel innerhalb eines geladenen Plugins.
local now = Turbine.Engine.GetGameTime()
local expiresAt = now + 12
local remaining = math.max(0, expiresAt - now)

Wenn du stattdessen „pro Frame 0,016 Sekunden abziehen“ programmierst, läuft der Timer abhängig von der Bildrate falsch. Ein Zeitstempel verkraftet auch eine unregelmäßige Aktualisierung: Nach einer Pause zeigt der nächste Frame die dann richtige Restzeit an.

Das Ereignis einschalten

Die folgende Erweiterung setzt das Fenster und Label aus Kapitel 2 voraus:

Lua 5.1
local expiresAt = Turbine.Engine.GetGameTime() + 12
local nextDrawAt = 0

window.Update = function(sender, args)
    local now = Turbine.Engine.GetGameTime()
    if now < nextDrawAt then
        return
    end
    nextDrawAt = now + 0.1 -- Anzeige hoechstens etwa zehnmal pro Sekunde

    local remaining = math.max(0, expiresAt - now)
    label:SetText(string.format("%.1f s", remaining))

    if remaining <= 0 then
        label:SetText("Abgelaufen")
        window:SetWantsUpdates(false)
    end
end

window:SetWantsUpdates(true)

Update wird bei aktivierten Updates framebezogen aufgerufen. Der frühe Rücksprung begrenzt die teurere Arbeit an der Oberfläche, nicht zwingend die Anzahl eingehender Events. Wenn der Timer vorbei ist, werden die Updates ganz ausgeschaltet. [8]

Das sichtbare Ende kann hier bis ungefähr zum nächsten Zeichenintervall verzögert erscheinen. Die zugrunde liegende Restzeit wird trotzdem aus Zeitpunkten berechnet und driftet nicht durch fortgesetztes Abziehen.

Zeitbasis nicht vermischen

GetGameTime() ist eine relative Spielzeit. Speichere solche Ablaufzeitpunkte nicht als dauerhaft gültige Kalenderzeit über Logins hinweg. Für unser Lernplugin leben Timer nur während der aktuellen Sitzung. Wenn du später Zeitangaben aus Effektobjekten verwendest, prüfe ihre dokumentierte Zeitbasis; eine andere Uhr darfst du nicht ohne Umrechnung davon abziehen.

Für persistente Daten verwendet ein Plugin Turbine.PluginData, nicht beliebige io.open-Dateizugriffe. Speichere einfache Werte und Datentabellen: Positionen, Farben, Aktivierung, konfigurierte Dauern. Fensterobjekte, Funktionen, Effektobjekte und laufende Closures gehören nicht in deine Einstellungsdatei.

A: Beim Laden lesen

Character ist für Einstellungen dieses Charakters passend. Account eignet sich für gemeinsame Einstellungen innerhalb des entsprechenden Kontobereichs. Ein präziser Schlüssel reduziert Namenskollisionen. Die zusätzliche Versionsnummer hilft später bei Änderungen der Datenstruktur.

Eigene Befehle und bewusstes Aufräumen

Ein eigener Slash-Befehl ist der bequemste Weg, ein geschlossenes Fenster wieder einzublenden oder einen Test auszulösen.

Lua 5.1
-- Ergaenzung zu Kapitel 2; window existiert bereits.
local command = Turbine.ShellCommand()

function command:Execute(commandName, arguments)
    if arguments == "show" then
        window:SetVisible(true)
    elseif arguments == "hide" then
        window:SetVisible(false)
    else
        Turbine.Shell.WriteLine("Benutze /lw show oder /lw hide")
    end
end

function command:GetHelp()
    return "/lw show | hide"
end

Turbine.Shell.AddCommand("lw", command)

plugin.Unload = function(sender, args)
    Turbine.Shell.RemoveCommand(command)
    window:SetWantsUpdates(false)
    window:SetVisible(false)
end

Bei /lw show ist commandName der Befehlsname und arguments der Text dahinter. Der Doppelpunkt bei Execute ergänzt zusätzlich self; du musst diesen Parameter nicht noch einmal ausdrücklich aufschreiben. Bei AddCommand steht der Name ohne Schrägstrich. [10]

Dieses Beispiel ist eigenständig zu Kapitel 2 gedacht. Es ersetzt die Unload-Zuweisung anderer Lernfassungen. In der endgültigen Fassung sammelst du alle Aufräumschritte in genau einem Handler.

Merksatz zum Lebenszyklus: Was du anmeldest, meldest du ab. Was Updates bekommt, stellst du ab. Was dauerhaft bleiben soll, speicherst du bewusst. Das ist weniger spektakulär als ein leuchtender Balken und langfristig sehr viel wertvoller.

    state.expiresAt = nil
    fill:SetVisible(false)
    label:SetText(message or "Gestoppt")
    window:SetWantsUpdates(false)
end

local function Render(now)
    if state.expiresAt == nil then
        window:SetWantsUpdates(false)
        return
    end

    local remaining = math.max(0, state.expiresAt - now)
    if remaining <= 0 then
        StopTimer("Abgelaufen")
        return
    end

    local fraction = math.min(1, remaining / state.duration)
    fill:SetWidth(math.max(1, math.floor(BAR_WIDTH * fraction)))
    fill:SetVisible(true)
    label:SetText(string.format("Testtimer: %.1f s", remaining))

    if remaining <= 3 then
        fill:SetBackColor(warningColor)
    else
        fill:SetBackColor(normalColor)
    end
end

local function StartTimer(duration)
    if type(duration) ~= "number" or duration ~= duration
        or duration < 1 or duration > 120 then
        Turbine.Shell.WriteLine("Dauer muss zwischen 1 und 120 liegen.")
        return
    end

    local now = Turbine.Engine.GetGameTime()
    state.duration = duration
    state.expiresAt = now + duration
    state.nextDrawAt = now + 0.1
    window:SetVisible(true)
    Render(now)
    window:SetWantsUpdates(true)
end

-- 5. Eigene UI-Ereignisse.
startButton.Click = function(sender, args)
    StartTimer(DEFAULT_DURATION)
end

stopButton.Click = function(sender, args)
    StopTimer("Gestoppt")
end

window.Update = function(sender, args)
    local now = Turbine.Engine.GetGameTime()
    if now < state.nextDrawAt then
        return
    end
    state.nextDrawAt = now + 0.1
    Render(now)
end

window.VisibleChanged = function(sender, args)
    if window:IsVisible() then
        Render(Turbine.Engine.GetGameTime())
        window:SetWantsUpdates(state.expiresAt ~= nil)
    else
        -- Die Zeit laeuft weiter, aber wir zeichnen nichts.
        window:SetWantsUpdates(false)
    end
end

-- 6. Slash-Befehl /lw.
local command = Turbine.ShellCommand()

function command:GetHelp()
    return "/lw show | hide | start [1-120] | stop"
end

function command:Execute(commandName, arguments)
    local action, value = string.match(
        arguments or "", "^%s*(%S*)%s*(.-)%s*$"
    )
    action = string.lower(action or "")

    if action == "" or action == "show" then
        window:SetVisible(true)
        Render(Turbine.Engine.GetGameTime())
    elseif action == "hide" then
        window:SetVisible(false)
    elseif action == "start" then
        local duration = DEFAULT_DURATION
        if value ~= "" then
            duration = tonumber(value)
        end
        StartTimer(duration)
    elseif action == "stop" then
        StopTimer("Gestoppt")
    else
        Turbine.Shell.WriteLine(self:GetHelp())
    end
end

Turbine.Shell.AddCommand("lw", command)

-- 7. Beim Entladen eigene Ressourcen aufraeumen.
plugin.Unload = function(sender, args)
    window:SetWantsUpdates(false)
    Turbine.Shell.RemoveCommand(command)
    window:SetVisible(false)
    window.Update = nil
    window.VisibleChanged = nil
    startButton.Click = nil
    stopButton.Click = nil
end

window:SetVisible(true)
Turbine.Shell.WriteLine("LuaWerkstatt bereit. /lw start 12")

Was dabei in welcher Reihenfolge geschieht

  1. Beim Laden: Zustand und Oberfläche werden angelegt. Funktionen und Handler werden definiert; /lw wird registriert.
  2. Beim Starten: Die Dauer wird geprüft und ein Ablaufzeitpunkt gespeichert. Das Fenster wird eingeblendet und die erste Anzeige sofort gezeichnet.
  3. Während des Countdowns: Update ruft gedrosselt Render auf. Dort entsteht die Restzeit aus Ablaufzeit minus aktueller Zeit.
  4. Beim Ausblenden: Das Zeichnen wird abgeschaltet. Der Ablaufzeitpunkt bleibt bestehen; erneutes Einblenden berücksichtigt die vergangene Zeit.
  5. Beim Ablauf oder Stoppen: Der aktive Zeitstempel wird entfernt, die Füllung verborgen und das Update abgeschaltet.
  6. Beim Entladen: Der Slash-Befehl und die eigenen UI-Handler werden entfernt.

Die Großschreibung von DEFAULT_DURATION ist nur eine Namenskonvention. Lua 5.1 erzwingt damit keine Unveränderlichkeit. Die etwas ungewöhnliche Prüfung duration ~= duration fängt einen möglichen NaN-Wert ab; normale Zahlen sind sich selbst gleich.

Solange dein Plugin klein ist, darf es ruhig in einer einzigen Datei leben. Sobald du mehrere Timeranzeigen und Einstellungen hast, lohnt sich eine Aufteilung.

import ist nicht einfach require mit anderem Namen

In gewöhnlichen Lua-Projekten siehst du häufig require. LOTRO besitzt sein eigenes import- und Paketsystem. Ein Import wie import "JulianPlugins.LuaWerkstatt.TimerModel" sucht die entsprechende Lua-Datei relativ zu Plugins. Wenn du einen Paketordner statt einer konkreten Datei importierst, begegnet dir häufig eine __init__.lua, die dessen Inhalte zusammenführt.

Ein local in einer importierten Datei wird nicht dadurch automatisch zu einer lokalen Variable in Main.lua. Plane daher ausdrücklich, was ein Modul nach außen bereitstellt. Nimm nicht an, dass local model = import "..." dasselbe Modulrückgabemuster wie Standard-Lua-require liefert.

Klassen ohne Zauberwort

Lua 5.1 besitzt kein eingebautes class-Schlüsselwort. Wenn du class(...) in einem Plugin liest, ist das eine bereitgestellte Hilfsfunktion. Ein einfaches eigenes Datenobjekt kannst du bereits mit Tabellen und einer Metatabelle bauen:

Lua 5.1
local Timer = {}
Timer.__index = Timer

function Timer.New(duration)
    assert(type(duration) == "number" and duration > 0)
    return setmetatable({
        duration = duration,
        expiresAt = nil
    }, Timer)
end

function Timer:Start(now)
    self.expiresAt = now + self.duration
end

function Timer:Remaining(now)
    if self.expiresAt == nil then
        return 0
    end
    return math.max(0, self.expiresAt - now)
end

local first = Timer.New(12)
local second = Timer.New(18)
first:Start(100)
second:Start(100)

Turbine.Shell.WriteLine(tostring(first:Remaining(105))) -- 7
Turbine.Shell.WriteLine(tostring(second:Remaining(105))) -- 13

setmetatable verbindet die neue Instanz mit Regeln. __index = Timer besagt vereinfacht: Wenn ein Feld in der Instanz fehlt, suche es in der Tabelle Timer. Dort liegen die Methoden, während jede Instanz ihre eigenen Zustandswerte besitzt.

Timer.New(12) ist hier absichtlich eine mit Punkt definierte Funktion. first:Start(100) ist eine Methode mit self. Diese eigene kleine Klasse ersetzt keine Turbine-UI-Klasse und versucht nicht, ihre Interna nachzubauen. Sie organisiert lediglich unsere Timerdaten.

Wann lohnt sich das? Sobald mehrere gleichartige Objekte dieselbe Logik brauchen. Für genau einen Balken ist eine handvoll lokaler Funktionen völlig anständig. Architektur ist ein Werkzeug, kein Adelstitel.

pcall fängt Laufzeitfehler ab – und ersetzt keine Reparatur

Lua 5.1
local function ReadBrokenSettings()
    error("Absichtlicher Testfehler")
end

local ok, result = pcall(ReadBrokenSettings)
if not ok then
    Turbine.Shell.WriteLine("Laden fehlgeschlagen: " .. tostring(result))
end

pcall liefert zuerst den Erfolgsstatus. Bei einem Fehler folgt dessen Meldung. Es hilft an begrenzten Schnittstellen, etwa beim Verarbeiten fremder gespeicherter Daten. Packst du wahllos dein ganzes Plugin hinein und verschweigst die Meldungen, hast du den Fehler lediglich unter den Teppich geschoben.

Syntaxfehler in derselben Datei entstehen schon beim Einlesen und werden durch einen späteren pcall nicht geheilt. Auch eine Endlosschleife verwandelt sich dadurch nicht in einen harmlosen Fehler.

Reproduzierbare Fehlerberichte

Notiere Pluginfassung, genaue Aktion, erwartetes Verhalten, tatsächliches Verhalten und die erste Fehlermeldung. Bei einem Chatparser gehören echte Rohmeldungen und die Clientsprache dazu. „Geht nicht“ ist menschlich verständlich, aber technisch ungefähr so ergiebig wie „Boot nass“.

Übungen mit Lösungen

Bearbeite zuerst die Aufgabe und öffne danach die Lösung. Die kleinen Experimente sind wichtiger als das Auswendiglernen aller API-Namen.

A · Wahr oder falsch?

Was wird ausgegeben?

Lua 5.1
local seconds = 0
local text = ""

if seconds and text then
    Turbine.Shell.WriteLine("A")
else
    Turbine.Shell.WriteLine("B")
end
Lösung anzeigen

A. Sowohl 0 als auch ein leerer String sind in Lua wahr. Wenn du einen laufenden Timer prüfen willst, brauchst du etwa seconds > 0; für nichtleeren Text text ~= "".

B · Eine saubere Restzeitfunktion

Schreibe eine Funktion, die für Ende 112 und Jetzt 115 den Wert 0 statt −3 liefert.

Lösung anzeigen
Lua 5.1
local function GetRemaining(expiresAt, now)
    return math.max(0, expiresAt - now)
end

assert(GetRemaining(112, 105) == 7)
assert(GetRemaining(112, 115) == 0)

assert bleibt bei einer wahren Bedingung still und erzeugt bei einer falschen einen Fehler. Hier prüfen wir Ergebnisse, nicht die Anzahl geschriebener Codezeilen.

C · Einstellungen kopieren

Du setzt local mine = defaults und änderst anschließend mine.duration. Warum verändert sich defaults.duration mit?

Lösung anzeigen

Die Zuweisung kopiert eine Referenz auf dieselbe Tabelle. Erzeuge eine neue Tabelle und kopiere die gewünschten Felder. Für verschachtelte Tabellen musst du entscheiden, welche Untertabellen ebenfalls unabhängig sein sollen.

D · Warnschwelle verändern

Ändere den vollständigen Timer so, dass er erst bei höchstens 2 Sekunden orange wird. Wo musst du eingreifen?

Lösung anzeigen

In Render: if remaining <= 2 then. Der Ablaufzeitpunkt bleibt unverändert; du änderst nur eine Darstellungsentscheidung. Als nächsten Schritt könntest du daraus eine Einstellung machen.

E · Drei Buttons, drei Laufzeiten

Erzeuge für 5, 12 und 20 Sekunden jeweils einen Button. Voraussetzung ist die vollständige Fassung aus Kapitel 18. Setze die Erweiterung nach der Definition von StartTimer ein und vergrößere das Fenster.

Eine mögliche Lösung anzeigen
Lua 5.1
window:SetHeight(270)
local testDurations = { 5, 12, 20 }

for index, duration in ipairs(testDurations) do
    local selectedDuration = duration
    local testButton = Turbine.UI.Lotro.Button()
    testButton:SetParent(window)
    testButton:SetPosition(20 + (index - 1) * 115, 190)
    testButton:SetSize(110, 25)
    testButton:SetText(selectedDuration .. " s")
    testButton.Click = function(sender, args)
        StartTimer(selectedDuration)

Die lokale Variable macht ausdrücklich sichtbar, welchen Wert die jeweilige Closure verwendet. Für die optionale Positionsbegrenzung aus Kapitel 16 musst du die neue Fensterhöhe ebenfalls berücksichtigen.

F · Ein Parser soll nicht jeden Tick als Start zählen

Du beobachtest drei Meldungen mit demselben Fertigkeitsnamen innerhalb von neun Sekunden. Kannst du daraus drei Anwendungen ableiten?

Lösung anzeigen

Nein. Es können unter anderem drei periodische Schadensmeldungen desselben Effekts sein. Du brauchst weitere verlässliche Merkmale. Fehlen diese, muss die Anzeige ihre Schätzung kenntlich machen oder auf ein anderes Startsignal zurückgreifen.

Dein sinnvoller Lernpfad

Du musst dieses Dokument nicht in einem Rutsch durcharbeiten. Für den Anfang sind drei praktische Etappen ausreichend:

  1. Eine funktionierende Werkbank

    Kapitel 1–5: Plugin anlegen, laden, Text ändern, Werte ausgeben. Danach verstehst du, welche Datei LOTRO lädt und wie eine Lua-Anweisung aussieht.

  2. Die Sprache im Griff

    Kapitel 6–10: Tabellen, Schleifen, Funktionen, Closures und Methoden. Baue kleine Timerdaten auf und rechne Restzeiten aus. Die Oberfläche darf dabei noch ausgesprochen unschön sein.

  3. Ein eigenes Werkzeug im Spiel

    Kapitel 11–18: Timerfenster starten, Befehle ergänzen, sauber entladen, Position speichern. Erst danach Buffs oder Kampfmeldungen als Datenquelle anschließen.

Für dein späteres Hüter-Werkzeug ist die sinnvolle Reihenfolge: mehrere manuelle Timer, eine klare Reihenfolge der Balken, konfigurierbare Dauern und anschließend ein separat überprüfter Ereignisadapter. Für einen Bufftracker auf deinem Runenbewahrer oder Beorninger ist der Anfangsscan deiner eigenen Effekte mit anschließendem Eventabonnement die naheliegende Fortsetzung.

Eine kleine, präzise Anzeige ist das bessere erste Ziel als ein Tracker, der schon beim Start alle denkbaren Klassen, Sprachen und Raidmechaniken beherrschen soll. Der erste Balken muss nicht ganz Mittelerde verwalten.
